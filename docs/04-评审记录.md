# 评审记录 · 三道门

按 Sext 晷刻 DAG 走纯 CLI 捷径：`N1→N2→N4→G1→N5b→G2→N6→G3→N7`。
评审门由独立视角执行，干活的一方不能自评通过。下面是每道门真实打回的东西。

## G1 设计评审 · 打回两次

### 打回一：契约缺少「反近因」，样本项目的核心机制被漏掉

**问题**：初版打分公式用的是标准 recency（越新权重越高）。但长期陪伴场景的核心特征是"偶尔想起久远的事"——一个只记得最近三天的人不像人，像上下文窗口。

**证据**：某长期陪伴项目的检索公式是
`score = s × (W_MIN + (W_MAX − W_MIN) × stale)`，陈旧度越高权重越大。

**修正**：打分公式加 `stale_mode` 开关。问"现在/我是谁"用 recency，其余用 stale。这不是参数调整，是两条不同的时间语义。

### 打回二：预算机制把 token 当目标函数

**问题**：初版用 `value_density = 分数 × 权重 / token成本` 排序。这个公式会让"便宜但一般"的条目挤掉"贵但重要"的条目——正是通用记忆系统的通病。

**修正**：改成三阶段硬顺序——A 按质量选、B 压表达、C 才砍内容。排序键改回纯分数，token 只用于降级顺序与同分决胜。

### 放行条件

- 每个抽象必须有可运行的最小实现，禁止只写接口不写实现
- 数据模型必须支持"旧事实失效但留痕"
- 必须有明确拒答路径

## G2 代码评审 · 打回四次（都是真 bug）

### 打回一：否定被抽成了肯定

**现象**：「我不太喜欢猫」被抽成 `喜欢 猫`（polarity=+1）。

**根因**：规则表里"不喜欢"要求连续匹配，而实际文本是"不太喜欢"，中间有"太"字。于是只匹配到"喜欢"这一条子串。

**修正**：加否定窗口检测——匹配到谓词后检查它前面 6 个字符内有无否定词。同时把谓词归一（"讨厌" → "喜欢" + 负极性），避免谓词爆炸。

### 打回二：极性反转时篡改了历史

**现象**：先说"不喜欢猫"再说"喜欢猫"，旧事实的 polarity 被直接改成 +1。

**根因**：`_resolve_fact` 的 INVALIDATE 分支执行的是 `UPDATE fact SET polarity=?`。

**修正**：旧条作废（保留原极性 + 状态置 invalidated），新条另立。历史不可篡改——不然时间旅行会看到"他一直喜欢猫"，那是假的。

### 打回三：状态槽 ID 碰撞导致状态丢失

**现象**：连续说「我搬到上海」「我以前住在北京」，最终状态只剩上海，北京那条消失了。

**根因**：`slot_id` 用 `int(t_event)` 做哈希，同一秒内的两次状态变更是同一个 ID，`INSERT OR IGNORE` 静默忽略了第二条。

**修正**：ID 用毫秒精度 + 值参与哈希。

### 打回四：FastAPI 把所有请求体当成 query 参数

**现象**：`POST /v1/recall` 报 `Field required: query.body`。

**根因**：文件启用了 `from __future__ import annotations`，Pydantic 模型又定义在 `create_app()` 函数内部，注解被延迟成字符串后 FastAPI 在模块命名空间里找不到这些类，退化成普通参数。

**修正**：模型移到模块顶层。

### 评审中发现的设计问题（非 bug）

**抽取层正则过重**。初版写了 10 条正则覆盖常见句型。问题：
- 自然语言的变体远比正则能覆盖的多，漏抽率高
- 硬匹配会把句子掰成错误结构（"我不太喜欢猫"就是例子）
- 规则越多，语义扩散越差

**修正**：抽取改为 LLM structured output 为主，正则砍到只剩 3 条最基础的模式做兜底。宁可漏抽——错抽会污染长期记忆，漏抽只是少一条。

配套的 prompt 改进（来自 2026 年主流实践）：
- 明确允许返回空列表（不加这句，模型会把"用户打了个招呼"也记成记忆）
- 要求每条 self-contained（"用户同意了第二个选项"三周后毫无用处）
- 限定每类最多 2 条（不限制就宁可多提）

## G3 终验 · 放行

### 验收项

| 项 | 结果 |
|---|---|
| 九类机制测试 | 15/15 通过 |
| 状态转移（旧值失效留痕） | 通过 |
| 时间旅行 | 通过 |
| 预算绝不超限 | 通过（200/500/1200 三档） |
| 极小预算保状态 | 通过（60 token 下状态仍在） |
| 拒答 | 通过 |
| 删除不可复活 | 通过 |
| 人格预算取舍 | 通过 |
| 服务接口 | 全通，含 OpenAPI 文档 |
| 可视化界面 | 正常渲染 |
| 三个月演示 | 状态变更、时间旅行、失效留痕全部正确 |

### 未达成的（明确记录，不藏）

1. **检索延迟偏高**：hash 模式下单次 800-1200ms。主要开销是每次操作新建 SQLite 连接 + 逐条算向量。十万条以内能接受，交互体验需要再优化。
2. **常驻活文档没有自动重建触发**，需要手动调接口或定时任务。
3. **关系抽取在 rule 模式下覆盖率很低**（只有 3 条模式），这是刻意的取舍，但意味着离线模式基本只能靠 LLM。
4. **多进程写同一库未验证**。
