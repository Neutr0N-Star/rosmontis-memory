# 主动记忆设计 · harness 层

## 0. 这一层要解决什么

现有系统解决的是「**她怎么想起来**」——被动记忆：对话进库，检索时浮现。

缺的是「**她自己决定记什么、改什么**」——主动记忆。

差别不在技术，在**主语**。被动记忆的主语是系统（系统决定抽什么、存什么），主动记忆的主语是她。

这条线往下推，会引出三件事：
1. 她需要**写的地方**（分层笔记本）
2. 她需要**改自己的能力**（自成长：改人设、热重载）
3. 她需要**知道什么时候该写**（这不能靠她自己想起来，得靠 harness 推）

## 1. 问题诊断：笔记本为什么变成流水账

这是整套设计里唯一必须先想清楚的问题。其余都是它的推论。

流水账的成因有三个，都能在数据层定位：

| 成因 | 数据层表现 | 解法 |
|---|---|---|
| 只记 what，不记 meaning | 条目是一条陈述，没有推断层 | 结构化字段强制填三段 |
| 写的时候没有读者意识 | 不知道写给谁看，于是什么都写 | 写入时显式声明"给三个月后的自己" |
| 没有淘汰机制 | 条目只增不减，价值被稀释 | 速记层定期清空，只有被提炼的才留 |

### 关键判断一：流水账不是「写得太少」，是「结构少了一层」

一条有意义的笔记必须有四段：

```
what     发生了什么（客观）
noticed  我注意到了什么（观察，别人可能没注意的）
means    对我来说意味着什么（推断，可以错）
next     下次我该怎么做（指令，给未来的自己）
```

只有 `what` 的是日志。有 `what + noticed` 的是观察。有四段全的才是**给未来的自己留的话**。

这四段不一定要全填——但**只有 what 的条目不允许进笔记层**。这是防流水账的硬闸。

### 关键判断二：分层不能按时间分，要按「将来什么时候用得上」分

按时间分层（今天/本周/更早）没有意义，因为使用时不按时间找。

按用途分：

| 层 | 什么时候被读 | 更新频率 | 上限 | 淘汰 |
|---|---|---|---|---|
| **速记** inbox | 当天整理时 | 每条都进 | 无硬限 | 整理后清空 |
| **笔记** notes | 写新笔记时参考 | 每天 promoted 几条 | 每主题 20 条 | 衰减 + 合并 |
| **沉淀** pages | 每轮对话都注入 | 每周重写 | 1500 字 | 不淘汰，只重写 |
| **人设** persona | 每轮对话都注入 | 极少改 | 7600 字 | 只改不删 |

四种层的消亡方式完全不同，这是它们必须分开的原因：
- 速记是**消耗品**，用完就清
- 笔记是**资产**，会衰减但能被强化
- 沉淀是**结论**，会被重写但不会被丢弃
- 人设是**身份**，几乎不衰减（0.1x）

### 关键判断三：「主动」不等于「自由」

如果让她随时随意改人设，两件事会发生：人格漂移（每天不一样）、越改越乱（改的比写的多）。

所以主动必须是**有闸门的主动**：

| 闸门 | 约束 | 为什么 |
|---|---|---|
| 频率闸 | 单次会话最多改 2 次人设 | 防抖。人不会每天推翻自己的性格 |
| 幅度闸 | 单次改动不超过 200 字；protected 条目不可删改 | 防越权。核心身份不许动 |
| 来源闸 | 改人设的素材必须来自已存在的笔记 | 防凭空。有据可查才叫成长 |
| 留痕闸 | 每次改动生成 diff，可回滚 | 防不可逆 |

四道闸合起来的效果是：**她可以成长，但不能突变**。

## 2. 核心模型：三个动作 + 一个触发器

### 三个动作（她自己调用的工具）

| 动作 | 语义 | 类比 |
|---|---|---|
| `remember` | 写一条笔记 | 记在本子上 |
| `revise` | 订正一条旧笔记 | 划掉重写，原文保留 |
| `promote` | 把笔记升格进沉淀或人设 | 从本子抄进「关于他」那一页 |

三个动作都是工具调用，由模型决定何时用。但**触发时机由 harness 给信号**——见下一节。

### 一个触发器：会话结束

这是上一轮加的 `close_session` 的自然延伸。

会话结束时，harness 做四件事：

```
1. 回顾：把这次会话里值得记的东西，提炼成 2-3 条笔记（不是全部）
2. 提问：给她一个"现在要不要改自己"的窗口，而不是每轮都问
3. 结算：峰终（已实现）
4. 沉淀：重建活文档（已实现）
```

为什么要放在会话结束而不是每轮：**每轮都问「你要不要写笔记」会让她变成一个一直在自我审视的怪物**。人也不是每句话后都写日记。

## 3. 与现有系统的结合点（最关键的一节）

原则：**不新建平行系统，全部寄生在现有结构上。**

| 新东西 | 寄生在哪 | 怎么寄生 |
|---|---|---|
| 笔记本条目 | `episode` 表 | 新增 `source='notebook'`，四段结构存 `meta_json` |
| 速记→笔记的升格 | 现有 `tier` 字段 | `tier='inbox'` → `tier='retrieval'` |
| 笔记→沉淀 | 现有 `pages` | `promote` 时把笔记内容并入对应 page |
| 笔记→人设 | 现有 `persona` | `promote` 时写一条 persona，`author='self'` |
| 笔记的检索 | 现有三路召回 | 零改动，因为已经是 episode |
| 笔记的衰减 | 现有三空间衰减率 | 映射到 `operational`（3.0x）——笔记不常用就该淡 |
| 笔记的重要性 | 现有 ACT-R 激活 | 零改动 |

**关键收益**：不写新检索、不写新遗忘、不写新存储。所有机制自动继承。

**代价**：`episode` 表要加一个 `tier='inbox'`。已经是 TEXT 字段，无需迁移。

### 唯一需要新建的表

`notebook_promotion`——记录"哪条笔记升到了哪里"，用于审计和回滚。

```sql
CREATE TABLE notebook_promotion (
    id           TEXT PRIMARY KEY,
    note_id      TEXT NOT NULL,     -- 源笔记
    target_type  TEXT NOT NULL,     -- page / persona
    target_id    TEXT NOT NULL,     -- 目标 id
    promoted_at  REAL NOT NULL,
    diff         TEXT,              -- 改动前后的差异
    reverted     INTEGER DEFAULT 0
);
```

就这一张。其余全部复用。

## 4. 热重载：改了立刻生效

现有 `persona_compile()` 每次调用都重新读库编译，所以「改了就生效」天然成立——**前提是调用方每次都调**。

大多数接入方不会每次调。所以要提供**一次调用拿全**的接口：

```
build_context(query) → {
    persona:  人格块（受 7600 字预算）
    resident: 常驻块（活文档，不检索）
    recalled: 检索块（按问题浮现）
    meta:     { tokens, depth, abstained, persona_version }
}
```

`persona_version` 是每次编译递增的版本号。接入方只需在每轮对话前调一次 `build_context`，人格改动自动生效——**这就是热重载的工程实现，不需要监听文件变化**。

## 5. 工具契约（给 agent 的 function calling）

```json
{
  "name": "notebook_remember",
  "parameters": {
    "what":    "发生了什么（必填）",
    "noticed": "我注意到了什么（可空，但空则不进笔记层）",
    "means":   "对我来说意味着什么（可空）",
    "next":    "下次我该怎么做（可空）",
    "topic":   "主题标签（用于归组）"
  }
}
```

```json
{
  "name": "notebook_promote",
  "parameters": {
    "note_id": "哪条笔记",
    "target":  "page | persona",
    "section": "升到人设时放哪个分区（identity/rule/speech/trait/taste）"
  }
}
```

```json
{
  "name": "self_revise",
  "parameters": {
    "note_id": "改哪条",
    "new_text": "新的说法",
    "reason":  "为什么改（必填，并入 meta）"
  }
}
```

三个工具都受闸门约束，超限返回明确原因而不是静默失败。

## 6. 防流水账的两个机制

### 机制一：写入闸

```python
if not noticed and not means and not next:
    tier = "inbox"        # 只有 what，进速记层，不进笔记层
else:
    tier = "retrieval"    # 有第二层，进笔记层，参与检索
```

### 机制二：整理闸

会话结束时，把速记层里只有 what 的条目做一次批量处理：
- 能提炼出第二层的（同主题多条合并）→ 升级
- 提炼不出的 → 直接丢弃（**这是"遗忘"在主动层的对应物**）

这一步是防"笔记层被流水账塞满"的兜底。没有它，写入闸只是延后了问题。

## 7. 验收标准

| 编号 | 标准 | 判定方式 |
|---|---|---|
| A1 | 只有 what 的条目不会进笔记层 | 写一条纯陈述，查 tier 必须是 inbox |
| A2 | 有四段的条目能进笔记层并被检索到 | 写一条完整笔记，recall 能命中 |
| A3 | 笔记升格到人设后，`build_context` 立刻反映 | 改完立即调 build_context，persona 含新条目 |
| A4 | 人设改动受频率闸限制 | 单次会话第 3 次 promote 被拒 |
| A5 | 人设改动受幅度闸限制 | 改 protected 条目被拒 |
| A6 | 改动可回滚 | promote 后 revert，persona 回到原状 |
| A7 | 速记层被整理后清空 | close_session 后 inbox 为空 |
| A8 | 笔记继承现有遗忘机制 | 笔记长时间不召回后进入衰减区间 |

## 8. 不做什么

- **不做自动写日记**。写不写、写什么，是她自己的判断。harness 只提供工具和时机，不替她写。
- **不做人格自动演进**。人设只能由她基于笔记主动 promote，不能被系统"推断"出来。
- **不做笔记本的独立前端**。笔记本是记忆的一种来源，不是独立产品。要看得见，走现有的 `/v1/episodes?source=notebook`。
- **不引入新的检索通道**。笔记就是 episode，复用三路召回。
