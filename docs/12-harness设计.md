# Harness 设计 · 熏习

## 0. 本体：harness 是什么

**Harness = 包在模型外面的一圈固定流程，让记忆在对话里自动发生。**

它不是一个东西，是三个东西的合称：

| 组成 | 做什么 |
|---|---|
| **一圈循环** | 每轮对话固定做四件事：记录 → 取上下文 → 调模型 → 执行工具 |
| **一套工具** | 让模型能主动写、主动查、主动升格，而不是只能被动被检索 |
| **一个节拍** | 到点整理、到点做梦，不靠模型自己想起来 |

它解决的是一个问题：**记忆系统做得再好，接入方不调用就等于不存在。**

前面的模块都是"能力"，harness 是"把能力接进对话"的那根线。

## 1. 隐喻：为什么叫熏习

唯识里有一对概念，正好对应这套系统的双向流动：

```
种子 → 现行      记忆影响行为（她记得他怕黑，所以不关灯）
现行 → 熏种子    行为改变记忆（今天又聊了一次，这条记忆被强化）
```

**这两个方向必须同时发生，缺一个系统就是死的。**

- 只有"种子→现行"：记忆只出不进，是一个只读的知识库
- 只有"现行→熏种子"：记忆只进不出，是一个只写的日志

harness 就是这两个方向交汇的地方。所以这一层叫 **熏习**（vāsanā）——不是"存储"，是"熏陶与习染"。

三个生命周期沿用最朴素的说法：

| 方法 | 隐喻 | 做什么 |
|---|---|---|
| `wake` | 醒 | 会话开始：播种、载入人格 |
| `turn` | 一息 | 一轮对话：记录 → 取上下文 → 生成 → 执行工具 |
| `sleep` | 眠 | 会话结束：峰终结算、整理锦囊、可能做梦 |

用"醒/一息/眠"而不是"start/step/end"，是因为这三个词本身就说明了**该做什么、不该做什么**：醒着的时候做事，睡着的时候加工。

## 2. 和被动系统的关系：谁调谁

这一节是关键，容易搞反。

```
        ┌─────────────────────────────┐
        │  接入方（前端 / 别的 agent）  │
        └──────────────┬──────────────┘
                       │ 只调 harness
                       ▼
        ┌─────────────────────────────┐
        │  Harness（熏习）              │
        │  醒 → 一息*N → 眠            │
        └──────────────┬──────────────┘
                       │ 内部编排
        ┌──────────────┴──────────────┐
        │  被动系统（recall / ingest）  │
        │  主动系统（notebook / dream） │
        │  人格（persona）              │
        └─────────────────────────────┘
```

**接入方只跟 harness 打交道，不直接碰记忆模块。**

理由：如果接入方自己决定"什么时候 recall、recall 多少、什么时候存"，那每个接入方都会做成一坨不同的东西，而且十有八九会漏掉某些环节（比如忘了存模型自己说的话）。

harness 把这些固化下来，接入方只需要：把用户说的话交给它，接住它返回的回复。

### 被动系统在哪些点被用上

| 时机 | 调什么 | 为什么 |
|---|---|---|
| 每轮生成前 | `build_context()` | 一次拿全人格 + 常驻 + 检索 |
| 用户说话后 | `ingest(role='user')` | 记下来，后面才可能被检索到 |
| 模型回答后 | `ingest(role='assistant')` | **不对称的记忆是残的**——只记用户不记自己，她会不知道自己说过什么 |
| 模型主动查 | `recall()`（工具） | 想起来了才查，跟被动注入是两回事 |
| 会话结束 | `close_session()` | 峰终 + 整理 + 沉淀 |
| 任意时刻 | `tick()` | 到点整理 / 到点做梦 |

最后两行是异步的，不阻塞对话。

## 3. 一轮对话的完整时序

```
用户输入
  │
  ├─① ingest(user)              原文落库，不等抽取
  ├─② tick()                    轻量检查：该整理吗？该做梦吗？（异步，不阻塞）
  ├─③ build_context(query)      人格 + 常驻 + 检索，一次拿全
  ├─④ call_llm(system, messages)
  ├─⑤ 有 tool_calls？
  │    ├─ 是 → dispatch → 结果回灌 → 再调一次 LLM
  │    └─ 否 → 拿到回复
  ├─⑥ ingest(assistant)         记下她说了什么
  └─⑦ 返回 {reply, memory, tools}
```

三个容易做错的地方：

**第一，⑤ 必须有次数上限。** 工具调用可能循环（模型查了又查）。设 3 次上限，超了就带着已有结果收尾。

**第二，② 要异步。** `tick()` 里有 LLM 调用（做梦的抽象），同步会卡住对话。放进后台线程。

**第三，⑥ 不能省。** 很多接入方只记用户的话，结果她"不知道自己说过什么"，被问"你上次不是说…"就断片。

## 4. 工具契约

给模型五个工具。少而够用，太多会让她变成一个到处乱记的机器。

| 工具 | 什么时候用 | 副作用 |
|---|---|---|
| `alaya_remember` | 觉得这件事值得留给以后的自己 | 写一条笔记（可能进速记层） |
| `alaya_recall` | 想主动查一件事（不是被动注入的） | 无 |
| `alaya_promote` | 一条笔记反复想到，觉得该变成"我就是这样" | **改人设**，受闸门 |
| `alaya_revise` | 发现以前记错了 | 订正，原文保留 |
| `alaya_skip` | 不想再提某件事 | 降低激活，不删除 |

`alaya_skip` 这个工具很关键——它对应"这件事我不想再提了"。没有这个出口，所有记忆都只能靠衰减慢慢冷掉；有了它，她可以主动说"这个别再提"。

### 闸门在工具层的表现

`alaya_promote` 被拒绝时，**要返回明确原因，不能静默失败**：

```json
{"ok": false, "reason": "单次会话最多改 2 次人设（已用 2 次）。人格不该每天推翻"}
```

模型看到这个原因，会自己调整行为——这比系统硬压着不让改更自然。

## 5. 交付形态

| 文件 | 内容 |
|---|---|
| `alaya/harness.py` | `Harness` 类：wake / turn / sleep / tick |
| `alaya/tools.py` | 五个工具的 JSON schema + 统一 dispatcher |
| `demo/harness_demo.py` | 可运行的完整对话演示（mock LLM，不依赖任何模型） |
| `docs/12-harness设计.md` | 本文 |

`Harness` 不绑定任何 LLM SDK——它接收一个 `llm_callable(messages, tools) -> response`，你可以塞 OpenAI、Ollama、DeepSeek 或一个假模型进去。

## 6. 接入方最少要写多少代码

```python
h = Harness(cfg=Config(), llm_callable=my_llm)
h.wake("u1")

while True:
    text = input()
    r = h.turn(text, "u1")
    print(r["reply"])

h.sleep("u1")
```

四行。其余全在 harness 里。

## 7. 不做什么

- **不做 prompt 模板**。人格和记忆由 `build_context` 给出，但 system prompt 的整体结构由接入方决定——因为不同产品的说话方式差别太大，硬塞模板会打架。
- **不做多 agent 协调**。单会话单 agent。
- **不做前端**。这一层只出 Python 类和 HTTP 接口。
- **不替模型决定"该不该记"**。写不写、写什么，是模型自己调工具决定的。harness 只提供工具和时机。
