## 0 结论先行

1. **主被动不是两套记忆，是三个发起者的同一条记忆管线。** 现在是「两个写入口 + 两套语义 + 一条没接上的链路」，不是「两个库」。
2. 裂缝分三层：**派生层**（笔记无 fact/超边，被动抽取有）、**语义层**（tier/source 多套取值与四套重要度算法）、**链路层**（真实产品路径上主动侧根本没运行）。
3. 拍板：**A2 方案②「统一对象 + 状态机」**——`episode` 升为唯一 item 表，`state` 为生命周期真值，`tier/source` 降为兼容投影，schema v3 只加列。只在接口层统一（方案①）不解决派生与淘汰；事件/场（方案③）在 182 条真实数据上不划算。
4. **新增判据 M6：整合不接通不算整合。** 现在 `app.py:139-157` 的 `llm_call` 恒返回空 `tool_calls`、`app.py:159` `auto_tick=False`、前端不调 `/v1/tick`——五个主动工具在部署里是死代码，做梦/整理不会自己发生。「她主动记」目前只存在于 demo。
5. **主动记忆不能只靠模型举手。** 系统自己的整流（结算/整理/做梦）必须能产出 note，模型工具只是加速通道；但「自动写日记 / 自动改人设」仍是红线：系统只产**候选**，人设仍过 gate。
6. 产品主线取 A3 结论：**记忆运行时**（可嵌入库 + 本地守护进程），MCP 是渠道不是本体；最需要警惕的是 Letta。
7. **整合与产品化必须合并动 schema 一次**：A2 的 v3 迁移与 A3 的 space_id/鉴权/jobs 同窗口做，避免两次停服、两次回滚演练。

## 1 核心模型：三个发起者，一个对象

| 发起者 | 入口 | 现在写什么 | 整合后 |
|---|---|---|---|
| **用户输入**（被动） | `ingest_async` → `write.ingest` | episode + 后台 enrich 出 entity/fact/state/超边 | 走统一管线，`origin='ingest'` |
| **模型**（主动·工具） | `alaya_remember/promote/revise/skip` | 只写 episode+FTS；promote 绕过 `PR` 直写 persona | 走统一管线，`origin='tool'`，状态由 gate 定 |
| **系统**（主动·整流） | `tick / close_session / dream / review` | 只产 dream 条目与合并笔记 | **必须能产 note 候选**，`origin='system'` |

设计原则（本文确立，后续不得违背）：

1. **对象同一**：一条记忆就是一个 item；「被动/主动」只是 `origin`，不改变打分、衰减、检索、淘汰的行为。
2. **单一写入点**：`INSERT INTO episode` 只出现在管线模块；任何入口不得自算 salience、自定 tier。
3. **单一生命周期**：状态机（7 态）是唯一真值，`tier/source` 是对外兼容投影，双写至少一个版本。
4. **闸门单一**：升格/降级/静音经同一 `gate.decide()`；`PR.can_promote` 保留其中（15 项测试依赖它）。
5. **系统不越权**：系统发起的产出只能进 note 候选；进 resident/persona 必须过 gate 与留痕。

## 2 现状判断依据（引 A1）

六条硬证据，决定整合必须同时动「写侧」与「生命周期」：

1. 主动写入不产 entity/fact/state/超边 → 笔记永远进不了 graph 与图扩散（`notebook.py:86-108` vs `write.py:526-546`、`recall.py:509-561`）。
2. 重要度四套算法：`_salience`、笔记内联公式、梦硬编码 0.4、订正 +0.1（`write.py:461-474`、`notebook.py:81`、`dream.py:139`、`memory.py:540`）。
3. 升格两套闸两个落点：`Memory.promote → PR.can_promote`；`notebook.promote` 频率/幅度/来源三闸**完全绕过 PR** 直写 persona（`memory.py:507-511`、`notebook.py:201-217`）。
4. 生命周期覆盖不对称：forget 只扫 episode 且排除 resident；tick 只做 review+dream；fact 没有冷却与归档（`forget.py:53,75`、`memory.py:643-665`）。
5. `tier='inbox'` 在检索侧不被排除，与 docs/11 §九「不可检索」矛盾（`recall.py:603-616`）。
6. 三空间衰减是死代码（`memory_field.py:29-56` 无调用），docs/09「笔记映射 operational 3.0x」不成立。

**部署事实（本次最重要的发现）**：三个「她主动」的机制在真实部署里全部不运行——工具链（空 `tool_calls`）、节拍（`auto_tick=False`）、梦境（无人调 `/v1/tick`）。所以这条链的验收不能只看单测，必须看真实 `/v1/turn` 路径。

## 3 方案与验收

采用 A2 方案②，判据沿用其 M1–M5（写入单点 / 结构投影同构 / 打分单点 / 生命周期单点 / 闸门单点），本文**新增两条**：

| 编号 | 判据 | 判定方式 |
|---|---|---|
| M6 | **链路连通**：真实 `/v1/turn` 路径上，主动或系统发起的 note 在 24h 内真实产生 | 端到端脚本：mock LLM 触发一次 remember + 一次 sleep，检查库里 `origin IN ('tool','system')` 且 `state IN ('inbox','note')` 的行 ≥1 |
| M7 | **节拍自走**：无人为干预下，会话 idle 超时自动结算、到期任务自动执行 | 守护进程跑 30 分钟，jobs 表出现完成的 `settle/dream/review` 任务，无手动调用 |

状态机 7 态与转移表见 A2 §3.2，本文不复述；要点三条：`inbox` 默认**不可检索**（待 CEO 拍板 C2）；`promote_resident` 与 `promote_persona/page` 是两种动作；所有转移写 `item_state_log`。

## 4 harness 层：能不能用、缺什么、怎么补

harness 是产品本体的契约，不是框架。现有 `wake/turn/sleep/tick` 四方法能用，但只覆盖「接入方把循环交给我们」这一种形态。

### 4.1 五个硬缺口（按影响排序）

| 缺口 | 现状 | 后果 |
|---|---|---|
| 不带对话历史 | `_build_messages` 只发 system + 当轮输入（`harness.py:129-138`） | 指代消解、「刚才那个」会塌；记忆顶替不了上下文窗口 |
| 工具链不通 | 服务侧 `llm_call` 恒返回空 `tool_calls`（`app.py:139-157`） | 五个工具是死代码，主动记忆不产生 |
| 节拍不自走 | `auto_tick=False`，前端不调 tick（`app.py:159`） | 做梦/整理/结算永不自动发生 |
| 回调缺元数据 | `llm_callable` 不返回 `usage/finish_reason` | 成本与截断无法观测，token 台账做不了 |
| 注入长在 turn 里 | `turn` 内部拼 system 字符串（`harness.py:129`） | 宿主自管循环时只能复制逻辑 → 每个接入方做成一坨 |

### 4.2 补法（与 A3 §3 一致，本文只定优先级）

1. **注入抽成纯函数** `context(query, space, budget) -> 结构化对象`，`turn` 变成它的调用者。
2. **四钩子契约**：`session_start / pre_prompt / post_turn / session_end`，全部幂等、全部立即返回（`session_end` 只回 `job_id`）。
3. **`turn(history=None, extra_system=None)` + `turn_async`**，顺手修掉历史缺口。
4. **工具接通**：扩 `LLM.chat(tools)` 解析 `tool_calls`，补 `tool_call_id`，落 `usage`。
5. **节拍移进守护进程**（jobs 表 + 单写者队列 + 租约选主），harness 只保留「可选立即触发」。

### 4.3 四类接入方的取舍（引 A3 §3.2，不展开）

自建 agent（完整价值）｜Claude Code 类宿主（hooks 适配，能拿到常驻注入）｜MCP 客户端（只能拿五到六成价值：没有 wake/sleep）｜OpenAI function calling（理想形态，接通即完整）。**结论：MCP 不当本体，因为 MCP-only 会把最值钱的三层能力让掉。**

## 5 产品形态（引 A3 §6）

- **主线**：② 本地记忆服务 + MCP，内核同时以 ① pip 库发布；③ 托管延后（有付费客户才做）。
- **卖得出去的只有两块**：派生状态快照 + 不变式 + as-of 时间旅行；人格预算 + 升格四道闸。其余（会遗忘、会做梦、支持 MCP）是入场券。
- **第一威胁位 Letta**，次之 Hindsight（架构同构 + 有公开评测）、Zep（时序主张重叠）。
- **不许引用对标 benchmark 数字**，直到 M2 评测门跑出自己的数字（当前一个都没跑过）。

## 8 风险与反判据

- **假整合**：接口层统一而派生/淘汰仍分叉 → 反判据：任一入口仍自算 tier 或 salience，即判不成功。
- **双写投影失守**：`state` 与 `tier` 被两处代码改 → 两个真相复活；靠「单一写入口 + 一致性校验脚本」防（I11）。
- **迁移事故**：WAL 未 checkpoint、非单事务、非幂等 → 真库修复成本高于收益；W1 备份与副本试跑是硬门。
- **状态槽污染**（C4 放开后）：一条错误主动条目改掉 city → 必须留证据链与一键回滚。
- **系统越权**：系统整流直接改人设 → 违反红线；gate 必须拒绝 `origin='system'` 直进 persona。
- **产品化失焦**：先做托管/多租户 → 建议按 A3：有付费客户才启动 M3。
