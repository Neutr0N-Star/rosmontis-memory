## 0 结论先行

1. **`Harness` 这个类可以整个退役**：11 个方法里没有一行记忆算法，全是编排与转发。但 `harness.py` 里的**模块级函数**不能退——`build_context` 与 `dispatch` 是产品本体。
2. **宿主契约是四条，不是两条**。最常被漏掉的是「assistant 一侧也要回写」，漏了等于只记住用户单方面说的话。
3. **alaya 的形态是「服务优先、MCP 获客、库为辅」**，不是一个能 `import` 就生效的模块——它的价值一半在时序上（每轮注入、会话边界、节拍），时序必须宿主配合。
4. **embedding 现在被当成"可降级外挂"，与本项目定位矛盾**。三处硬伤：`_probe_done` 声明后从未使用（无断路）；降级期写入留 NULL 且全库无回算（降级时写下的记忆永久残废）；向量只有长度校验、没有 model/dim 身份（换模型即静默作废）。方向是「真实量必须在场、断路只为不卡、恢复即回算」，不是「关掉它」。
5. 开源验收指标建议钉成硬指标：**`git clone` 到「自己的项目里第一轮对话带上记忆」≤ 10 分钟**。

## 2 harness 层到底冗余不冗余

### 2.1 结论

**冗余的是「谁实现」，不是「有没有」。**

- 作为**编排器**：`Harness` 类完全可退役。任何成品 harness 的工具循环都比它更好用。
- 作为**注入点的承诺**：不可退役。工具 schema 替代不了它。

最直接的证据是 alaya 自己的服务层：`app.py:655` 写的是

```python
from ..harness import build_context as _build_context_pure
```

`POST /v1/context` **绕过了 `Harness` 类**，直接调模块级函数。`build_context` 的 docstring 也写明「不再把逻辑埋在 `turn` 里」。

### 2.2 为什么"只注入工具 schema"不够

工具解决的是**写作面**；读入面没有工具可替代：

| | 工具 schema | 每轮注入 |
|---|---|---|
| 触发条件 | 模型**想要**才查 | 模型**看到问题之前**已在上下文 |
| 召回率 | 取决于模型自觉与提示词纪律 | 100%（只要 `build_context` 有内容） |
| 额外延迟 | 每次多一轮模型往返 | 0 |
| 能否承载「每轮必注入」的设计 | 不能 | 能 |

alaya 的两条差异化卖点在语法上就依赖这个「必」：

- **状态槽每轮必注入**——「他住哪」是派生快照，不该由检索决定今天查不查；
- **人格 7600 字独立预算 + 常驻块 420 token**——三档预算互不挪用，意味着每轮都要把三块拼进去。

具体失效形态：上一轮他说「搬去上海了」，这一轮模型判断「不用调工具」→ 上下文里没有这件事 → 答「北京」。

`docs/17 §2` 已给出同一判断：MCP 拿不到「每轮自动注入 + 会话结算」，只能暴露检索工具，价值打五六折。

### 2.3 换宿主时会被继承或重做的隐式契约

`Harness` 虽小，下列决定是踩坑后留下的，替换时要么继承、要么重新回答：

1. 空回复必须抛错，**不能当正常回复写进记忆**（`_run_loop`，`harness.py:704-707`）；
2. 工具轮上限 3，超限后要带着已有结果再收一次尾（`:749-759`）；
3. 工具失败原因必须回灌给模型，不能吞（`:729-746`）；
4. `pure=True` 时套 `quiet_recall_log()`（`:144-146`），注入不污染访问计数；
5. `fit_memory_text` 整行丢弃，绝不截半句（`:104-126`）；
6. `turn_stream` 断流不写半截记忆（`:578-639`，5 项测试守着）；
7. `sleep` 三步各自 try/except，峰终挂了不能连累做梦（`:762-779`）。

## 3 宿主契约

### 3.1 四条必须项

| # | 宿主必须保证 | 对应 alaya 能力 | 漏了会怎样 |
|---|---|---|---|
| 1 | 模型调用**前**，把 `system_prefix + memory_text` 放进 system | `build_context(pure=True)` / `POST /v1/context` | 降级成检索库，人格与状态槽失效 |
| 2 | 每轮 **user 与 assistant 两条**都回写 | `ingest_async` / `POST /v1/episodes` | 被动抽取、峰终结算、做梦材料缺一半 |
| 3 | 把 5 个工具 schema 交给模型并执行结果 | `dispatch` / 五个 HTTP 端点 | 主动记忆只剩 system 通道 |
| 4 | 有地方按时间敲维护 | `Memory.tick` / `POST /v1/tick` | 整理与做梦永不发生 |

第 2 条是最常漏的：多数接入只考虑"怎么把记忆喂进去"，忘了"怎么把对话记下来"。

### 3.2 一条否决项

**宿主不能改写或重排注入内容。** 典型反例：前端类项目自带 world info / 全局提示词槽位，会覆盖或压缩 system 消息；部分成品 harness 会自行重排 system。被改写的注入等于没注入。

### 3.3 分档判定

拿下面五问量任何一个候选宿主：

1. 模型请求前，有没有一个可修改的"拼 prompt"位置？
2. 每轮的 user 文本与 assistant 文本能不能拿到？
3. 请求体能不能塞 `tools`，或能不能挂 MCP / 插件？
4. 有没有定时器或后台任务的落脚点？
5. 它的身份键是「人」还是「会话」？

| 满足 | 档位 | 能拿到的价值 |
|---|---|---|
| 缺 1 | 不成立 | 只能当外部检索工具用，不构成接入 |
| 1 + 2 | 被动记忆 | 抽取、状态、召回、遗忘 |
| 1 + 2 + 3 | 主动记忆（工具通道） | `origin='tool'` 落库 |
| 1 + 2 + 3 + 4 | 完整 | 含 `origin='system'` 整流与 `origin='dream'` |
| 第 5 问答错 | 会失忆 | 记忆挂会话上，切场景即丢人 |

## 4 参考宿主案例：ai-companion-kit

外部对象：[pinganbbOvO/ai-companion-kit](https://github.com/pinganbbOvO/ai-companion-kit)，MIT，163★/11 fork，创建 2026-10-08，活跃。技术栈 Node ≥18、纯 ESM、无构建，`packages/companion` 零运行时依赖。

### 4.1 它有两套形态，接入点完全不同

| | `packages/companion`（独立包） | 桥接版（仓库主线教程） |
|---|---|---|
| 链路 | OneBot WS → Waker → Brain → OpenAI 兼容接口 | QQ → SnowLuma → qq-bridge（**外部仓库**）→ 成品 harness（HTTP）→ 分条发出 |
| 谁拥有循环 | `Brain` | 成品 harness |
| 记忆在哪 | `src/memory.js` 的 `people.json` / `turns.jsonl` | 桥接 state + `qq_*` MCP 工具 |
| alaya 落点 | 构造注入 `new Brain({ memory })` | MCP server |

桥接本体不在该仓库，仓库出的是补丁与教程；两套形态不能混谈。

### 4.2 它的记忆现状（决定了缺口在哪）

纯文本两个文件，无 sqlite、无向量库：

- `people.json`：按 QQ 号存 `name / traits / facts / topics / pending / interactions`，硬顶 40 / 60 / 20 / 12；
- `turns.jsonl`：跨场合对话流，≤400 条。

召回策略是纯「最近」：各数组取末尾若干条拼成一段中文 + 最近 20 轮。因此存在四类结构性短板：无相关度与时间衰减、旧事实不失效（新旧矛盾一起交给模型挑）、无法按时刻回看、超限静默截断且无留痕。这正好是 alaya 的 State/Fact 双时间与遗忘机制要解决的问题。

### 4.3 代码级接入点

- `Memory` 的同构面（据其 README 与 `Brain` 调用点）：`person / remember / touch / logTurn / recentTurns / renderPerson / renderRecent / dump`；
- **硬约束**：`renderPerson` / `renderRecent` 在 `Brain.reply()` 内是**同步调用**，HTTP 适配器必须本地留快照 + 异步 push，或把调用点改成 `await`；
- 节拍：其自身无后台定时器，需宿主新增（idle 触发）。

### 4.4 这个案例暴露的 alaya 缺口

| 缺口 | 说明 |
|---|---|
| `space` / `conversation` 两层缺失 | 全库只有 `session_id`，既是租户键又是对话键。陪聊需要「人（跨场景）× 聊天（场景）」两层，现在只能二选一（`docs/_wip/A3` §2.1-G1 已列） |
| `POST /v1/observe` 不存在 | 非 Python 宿主拿不到幂等回写（见 §1.3） |
| embedding 只有 `ollama` / `hash`，无内置路径 | 目标用户可能只有一个 OpenAI 兼容的对话 key，没有 embedding 通道；也没有零配置的本地真实量可用 |
| 无 daemon | 自动整理/做梦要靠宿主自己写定时器 |

## 5 三个真实阻塞（按首次接入的失败顺序）

### B1 embedding 被当成"可降级外挂"（最致命）

本项目的核心能力是向量检索，因此 embedding 不是可选依赖。当前实现把它当外挂处理，留下三处硬伤。

**B1a 没有断路，只有降级标记**

- `__init__` 声明了 `self._probe_done = False`（`embed.py:51`），**全文件再无引用**；
- `embed()` 在每个 cache miss 上都会调 `_embed_remote()`（`:61`），`degraded` 只在失败后置位，**不短路后续调用**（`:63-70`）；
- `_embed_remote` 用 `timeout=self.timeout`（默认 8s，`:113`）。

| 情形 | 实际表现 |
|---|---|
| 没装 Ollama（连接被拒） | 快速失败。功能仍可用，但每次 cache miss 都多一次失败连接 |
| Ollama 半死（TCP 通但不应答） | **每次 cache miss 等满 8s**，且降级后仍继续尝试。一轮对话含 1 次检索 + 1~2 次写入，即 2~3 次超时 |

断路要解决的是"不卡"，不是"关掉向量"。`docs/_wip/A3` §4.2 已记录该情形但未修。

**B1b 降级期写入的向量永不回算**

`write.py:97-99` 与 `notebook.py:90-91` 在 `degraded` 时不写向量，落库为 NULL。全库**没有任何回算任务**，因此：

- 降级期间写下的每一条记忆，恢复后仍永久缺向量，退出稠密召回；
- 这些条目只可能被 FTS 或图通道捞回，且永远补不齐。

这比"卡 8 秒"严重得多：**降级是有损且不可逆的**。

**B1c 向量没有身份，换模型即静默作废**

维度是全局配置（`config.py:153`，`ALAYA_EMBED_DIM` 默认 1024）；检索时只做字节长度校验，不符的行跳过并打一条 warning（`recall.py:641-646`、`field.py:186`）。库里没有记录每条向量由哪个模型、哪个维度产生，因此：

- 换 embedding 模型 → 旧向量静默失效，无提示、无迁移；
- 改维度 → 旧向量全部作废；
- 混用两种模型 → 长度一致时**不会被发现**，余弦相似度直接失真。

**现有降级路径本身是做过设计的，不应删**

`recall.py:276-288` 按 embedding 质量分三档调 rel 门：真语义向量 0.40、degraded 0.25、hash provider 直接跳过 rel 门（注释写明"它的余弦没有语义意义"）。这说明代码已经知道 hash 不是向量。问题不在降级逻辑，而在**降级被当成常态、且不可恢复**。

因此 `hash` 这个 provider 的定位应当收窄：保留给测试，不再作为对外的正式运行模式；对外列出"语义模式 / 无向量模式"，不列"哈希向量模式"。

### B2 没有 MCP server

成品 harness / agent 宿主（Claude Code、Cursor 一类）唯一零改代码的入口是 MCP。`docs/17 §2` 把 MCP 列入 backlog，理由是"v1 主线是 HTTP"——这个判断对"自己接前端"成立，对"被成品宿主接入"不成立。

### B3 没有守护进程

`alaya serve` 是"起一个 HTTP 服务"，不是 daemon：无单实例锁、无 idle 自动 `tick`/`sleep`、无崩溃重启、无开机自启。结果是**每个宿主都要自己重写一遍节拍**，而节拍恰恰是 alaya「会成长」的兑现方式。

| **P0** | 两个最小宿主示例：Python 与 Node 各一，20~30 行，只走 HTTP，不依赖外部模型 | `examples/host_min.py`、`examples/host_min.mjs` | 照抄即可跑通「写两条 → 取 context → 敲 tick」 |
| **P1** | MCP server：五个工具 + `alaya_context` + `alaya_tick`；Python 实现，进程内 `import alaya`，stdio 通信，不起端口 | 新增 `alaya/mcp_server.py`（约 100~150 行）+ 注册说明 | 成品 harness 加一行配置即可调用；工具返回值与 `tools.dispatch` 完全一致 |
| **P2** | `alaya daemon`：单实例锁、idle 超时自动 `tick`/`sleep`、崩溃重启、日志轮转 | 新增 CLI 子命令 + 调度线程 | 宿主完全不写定时器的情况下，整理与做梦按点发生 |
| **P3** | 宿主契约文档 + 两个真实宿主案例 | 新增 `HOST-CONTRACT.md`；案例一用日常在用的宿主，案例二用外部项目 | 第三方照文档能判断自己属于哪一档、缺哪一条 |

顺序理由：P0 决定"第一次接触会不会失败"；P1 决定"成品宿主能不能零改代码接入"；P2 决定"接上之后是不是真的会成长"；P3 是把已经成立的东西固化下来。

### 6.1 内置模型的发布样态

参照对象：[tswawa/WechatVibe](https://github.com/tswawa/WechatVibe)（Apache-2.0）内置 Laya 多语言 ONNX 模型（约 3.22 亿参数，纯 CPU 可跑）的做法。

**先纠正一个常见印象：它的标准包并不含模型。** 公开发行是「无模型标准包 + 独立模型包」，模型约 599MB 压缩 / 681MB 解压，由应用引导下载；只有 `build:portable` 生成的便携版才把模型打进产物。真正值得照搬的不是"把模型塞进包"，而是**把模型当成可安装资产**。

它的五条做法：

1. **代码与模型分离发布**：标准运行包不含模型，模型是独立资产。
2. **应用内引导下载**：下载器带断点续传（`.part`）、最多 3 次重试、大小 + SHA-256 双校验，**校验通过才替换旧文件，强制下载失败不删除已有模型**。
3. **可指向外部模型目录**：环境变量 + 命令行参数，源码与桌面产物各自有下载入口。
4. **推理在进程内**：onnxruntime，CPU 默认 4 线程；GPU 可选，不可用时回退 CPU；不依赖任何外部模型服务。
5. **两种产物**：标准包 + 独立模型包对外发行；便携版内嵌模型给离线场景。

对应到 alaya：

| 层 | 做法 |
|---|---|
| 安装 | `pip install alaya-memory` 仍只装核心（标准库可跑）；`pip install alaya-memory[embed]` 增加 onnxruntime + tokenizers |
| 模型资产 | 不进 PyPI。放 GitHub Release + HuggingFace / ModelScope 双源，随附 SHA-256 清单 |
| 安装命令 | `alaya models install <name>`：断点续传、双校验、失败保留旧模型；`alaya models list / where` |
| 模型目录 | 默认 `~/.alaya/models/<model>/`；`ALAYA_MODEL_DIR` 可指向已有目录或随应用分发的目录 |
| 缺失时 | 不崩溃：`/readyz` 报 `vector_mode: none, model: missing` 并给出安装命令；`ALAYA_EMBED_FALLBACK=error` 时启动失败 |
| Docker | `slim` 变体不含模型；`-models` 变体含模型；或挂 volume 到 `ALAYA_MODEL_DIR` |
| 模型档位 | `bge-small-zh-v1.5`（512 维，默认档，体积小、CPU 快）；`bge-m3`（1024 维，重型档，与现默认维度一致） |
| 验收 | `pytest -m model`：真实加载 ONNX，跑中文召回与拒答（对应其 `npm run test:model`） |
| 工程拆分 | 下载 / 校验 / 安装 / 路径解析分成独立模块，与推理适配器解耦（其 `model_source.py` / `model_install.py` / `model_bundle.py` / `local_model_source.py` 是同样拆法） |

**与 §5-B1c 的依赖**：两档维度不同（512 / 1024），因此**向量身份必须先落地**再切默认档，否则两代库混用会静默失真。建议顺序：先做向量身份与回算 → 再引入 `local` 通道 → 再改默认档。

**与 §5-B1a 的关系**：内置通道让"降级"从常态变回例外。断路器仍然要做，但它保护的是"模型损坏 / 目录被移走 / 磁盘满"这类异常，而不是"用户没装 Ollama"这种常态。
