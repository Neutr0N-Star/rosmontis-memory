## 0 摘要

C2=B（inbox 速记可整理但不出声）从「只有状态真值」接成「召回真的按状态过滤」：

- `archived / muted` **恒不可见**；`inbox` **默认不可见**，`Config.inbox_retrievable`（默认 `False`，环境变量 `ALAYA_INBOX_RETRIEVABLE`）打开后可被检索；`note / resident / important` 照旧可见；`dream` 沿用既有 `source='dream'` 排除。
- 四条候选来源（dense / sparse / graph / field）与常驻层使用**同一套** `item.recall_visible()` 判据；最终 `_load_candidate()` 还有一道兜底门。
- v2 旧库（无 `episode.state` 列）或 `state IS NULL`：用 `item.compat_state(tier, archived, muted)` 兜底，不抛错；真库只读副本实测通过。
- `retrieval_log.plan_json` 新增 `filtered_by_state`（被状态挡下的候选计数）与 `inbox_retrievable`（本次召回生效的开关值）。
- 新增 `tests/test_visibility.py` 8 项；既有 `test_all(15) + test_field(20) + test_items(22) + test_api(20)` 全绿。

A6 §5.6 已写明「WS-C 直接调用 `field` 契约函数前需 `bind(cfg, embedder)`」，本轮不重复追加。

### 2.2 `alaya/core/recall.py`

新增可见性小层（文件顶部，紧跟意图关键词）：

| 函数 | 作用 |
|---|---|
| `_has_column(cfg, table, col)` | `PRAGMA table_info` 探测列是否存在，按 `(db 路径, 表, 列)` 缓存；用于 v2/v3 分流 |
| `_episode_state(row)` | 取 `state`；为空（旧库无列或 NULL）时用 `IT.compat_state(tier, archived, muted)` 兼容投影 |
| `_state_visible(cfg, state)` | `IT.recall_visible(state)` 为真即可见；`inbox` 再看 `cfg.inbox_retrievable` |
| `_visible_keys(cfg, keys, plan)` | 批量过滤 `"kind:id"` 列表（场路/图路用），一次 SQL 回表，隐藏数计入 plan |
| `_note_filtered(plan, n)` | 累计 `plan["_filtered_by_state"]` |
| `_finalize_plan(plan, cfg)` | 把内部计数落成 `filtered_by_state`、`inbox_retrievable` |

四条来源的接线方式：

| 来源 | 过滤点 | 计数 |
|---|---|---|
| dense | SQL 只保留 `source!='dream'`，余弦算完后在 Python 按状态过滤，再取 top-k | `filtered_by_state += 1` / 隐藏命中 |
| sparse | FTS 排名不预过滤；episode 取数窗口放大到 `2k`，Python 过滤后再截到 `k` 条可见（避免隐藏条目把可见条目挤空） | 同上 |
| graph | 实体邻域/超边成员拼完后，`_visible_keys()` 批量过滤 episode | 批量计数 |
| field | ① 点着的种子先过滤（隐藏条目不参与扩散）；② 扩散得到的 `phi` 里 fact/episode 再过滤（`phi_top` 也只记可见节点） | 两处批量计数 |
| 常驻层 | `_collect_states()` 的 `tier='resident'` 行同样过 `_episode_visible()` | 计数 |
| 兜底门 | `_load_candidate()` 的 episode 分支先判状态（v2 无列时走兼容投影）；fact 分支判 `archived` | episode 隐藏计数 |

计数口径：**按「候选在某一路上被挡下的次数」累计**；同一条隐藏条目被 dense 和 sparse 同时命中会被计两次。这是审计用的量级指标，不是去重后的 item 数（如需唯一计数，可在 `_note_filtered` 传入 id 集合再改，接口已预留）。

`plan_json` 最终新增：

```json
{
  "inbox_retrievable": false,
  "filtered_by_state": 3,
  "...": "既有字段（seeds/iterations/edge_types/phi_top 等）不变"
}
```

## 5 风险与后续

1. **`_has_column` 缓存按库路径常驻**：正常路径是先 `DB.init_db()`（迁移到 v3）再召回，缓存不会过期；若同一进程内先召回 v2、再对该库执行迁移，需要清 `recall._SCHEMA_CAPS`。当前没有这种调用顺序（`Memory` 初始化即迁移）。
2. **`filtered_by_state` 是路线级计数**，同一隐藏 item 可能被多条路各计一次；报告/审计应按量级解读。若需要唯一 item 数，可把 `_note_filtered` 改成收 id 集合。
3. **开关是全局的**：`inbox_retrievable` 只支持整库/整进程放开，没有 per-session / per-query 覆盖；C2 的产品口径是默认不出声，调试/迁移时才打开，够用。
4. **dream 沿用源过滤**：dense/sparse 的 `source!='dream'` 未扩展到 graph/field；若 dream 条目挂在超边里，理论上仍可能经 graph 路成为候选。这是既有行为，本轮未改语义；若要收口，建议把 `source!='dream'` 并进同一套可见性判据（需要产品确认 dream 是否允许被结构路想起）。
5. **对 WS-C/调用方的影响**：inbox 条目现在对 `recall` 不可见是**行为变更**；`alaya_remember` 只有 what 的条目不会出现在 `alaya_recall` 结果里（符合 C2）。需要读 inbox 的整理流程请走 `notebook`/`tools` 的 inbox 查询接口，不要依赖 recall。
6. **fact.archived**：v3 起 `fact.archived=1` 会被 dense/sparse/load 过滤（不计数）；v2 无该列不过滤。若 WS-A 后续调整 fact 归档语义，保持该口径即可。
