# A3 产品形态与接入

> 研究问题：这套东西怎么从「跑得起来的工程 demo」变成「卖得出去的产品」。重心在接入契约与 harness 运用，不在界面。
> 证据基线：`README.md`、[需求确认单](../01-需求确认单.md)、[产品蓝图](../02-产品蓝图.md)、[架构契约](../03-技术方案与契约.md)、[复验报告](../08-复验报告.md)、[主动记忆设计](../09-主动记忆设计.md)、[harness 设计](../12-harness设计.md)、[迭代图](../13-迭代图.md)，以及 `alaya/harness.py`、`alaya/service/app.py`、`alaya/config.py`、`alaya/core/{memory,db,llm,embed,pages,recall}.py`、`tests/test_all.py`。
> 日期：2026-10-19 ｜ 竞品证据以 2026 年公开页面为准，链接见 §5；未核实处标「待验证」。

## 0. 结论先行

1. 现在的 Alaya 是**一个内核 + 一个样板接入**。内核（五层投影、双时间、预算注入、主动记忆）已有机制证明；样板接入（单进程 FastAPI + 单文件前端 + 全局 Harness 单例）不是产品形态。
2. 真正的产品资产不是前端，是**「唤醒 → 注入 → 回写 → 休眠」这套生命周期契约**。谁拥有对话循环，谁就必须能挂上这四个钩子；挂不上的接入方只能拿到检索工具，拿不到人格连续性。
3. 推荐主线：**「记忆运行时」——可嵌入库 + 本地守护进程，harness 作为契约而不是框架**。MCP、OpenAI function calling 是接入渠道，不是产品本体；托管 API 等有付费客户再做（M3）。
4. 不补就卖不出去：身份与隔离、后台任务可靠性、会话生命周期、质量可证明、并发与多进程写；另外密钥模型与成本可见性是硬门槛。
5. 成本不是第一矛盾（云模型下记忆层自身约 ¥1/天/活跃用户量级，见 §4.2），**同步「打烊」与无熔断的降级**才是体验与账单的爆点。
6. 最有威胁的竞品不是 mem0，是 **Letta**：它已经在讲「有状态身份 + dreaming + 自改记忆 + MCP」，开源、有 CLI/桌面、$20/月。见 §5.3。

## 1. 现状坐标

| 维度 | 现在 | 产品化要求 | 差距 |
|---|---|---|---|
| 形态 | 进程内库 `Memory` + 单进程服务 `alaya serve`（uvicorn 默认单 worker，`alaya/cli.py:32`） | 库 / 守护进程 / 容器 / 托管四档，可装可升级 | 打包与部署件全缺（无 pyproject、无 Dockerfile、无版本发布） |

| 后台 | 线程池 2 worker 做抽取（`alaya/core/memory.py:122`）；harness 后台 tick 最多 2 个且满了静默丢弃（`alaya/harness.py:232`） | 持久任务队列 + 重试 + 补偿扫描 | 进程退出即丢结构，无补偿 |

| 观测 | `/v1/stats`（调用数/失败数/降级）、`retrieval_log`、`TurnResult` 带 latency/token | 指标落库 + 聚合 + 告警 + 成本计量 | 无指标持久化、无成本台账、无 trace id |

## 2. 产品缺口清单

### 2.1 不补就卖不出去

| 编号 | 缺口 | 证据 | 后果 | 补齐动作 |
|---|---|---|---|---|
| G1 | **没有用户/空间层，只有会话**。`session_id` 既是隔离键又是对话键，且由调用方传入 | `alaya/service/app.py:52` 只拦 `*`；任意 session 可读；`README` 已知限制「跨会话共享没做」 | 同一用户换设备/换会话即失忆；多客户端无法共享；越权读取只需猜到 id | 引入 `space_id`（=用户/记忆空间）+ `conversation_id`；API 从 token 推导 space；对象级授权（id→space 校验） |
| G2 | **无鉴权、无配额、无租户** | `app.py` 全文件无 auth 依赖；CORS `*`（`app.py:244`）；`/v1/wipe` 无确认 | 只能跑在本机 loopback；任何对外部署都是数据事故 | Bearer token / API key、按 space 限流、危险接口二次确认 |
| G3 | **后台任务不可靠**：内存线程池、队列无界、失败只 debug 日志、无补偿扫描 | `memory.py:122-133`，grep 无 backfill | 崩溃/重启后原文在、结构永久缺；积压时延迟不可见 | `jobs` 表（kind/attempts/next_run/status）+ 轮询 worker + 退避 + 死信 + 启动扫描 |
| G4 | **会话生命周期靠调用方显式触发**：不打烊就没有峰终/沉淀/遗忘 | `harness.py:192`；README 已知限制 | 产品里「她越用越懂你」不成立，用户看不到成长 | 服务端 idle 超时自动 sleep；守护进程按节拍扫 space |
| G5 | **质量不可证明**：无真实语料回归集，拒答阈值 0.18/0.24/0.46 是初始值 | `docs/13` 第六轮：「没有标注数据，阈值只能猜」 | 无法承诺「比 mem0 好」；调参靠手感，发版即回归 | golden set + 六指标 + nightly 回归门（§4.4） |
| G6 | **并发与多进程没有契约**：单进程假设、读路径也写库、同会话无锁 | `recall.py:820` 每次检索写 `retrieval_log`；`memory.py:178` 每次检索写 `_touch`；`db.py` 2 次退避、busy_timeout 3s | 多 worker 各自持池、重复节拍；高并发下写锁排队 | 单写者队列（actor）+ 读路径日志异步化 + 会话锁 + 多进程租约（§3.4） |
| G7 | **密钥与成本不成立**：密钥明文落 `.env`（Windows 下 chmod 600 无效），设置接口可写任意 `openai_base` | `app.py:75-89`、`app.py:466`；`config.py` 无 KMS 概念 | 托管/多用户时密钥外带与 SSRF；账单不可控 | 服务端密钥库/环境注入、禁止运行时改 base、token 计量落库与预算闸 |

### 2.2 不补也能用（先别做）

| 缺口 | 现状 | 为什么可以先不做 |
|---|---|---|
| ANN 索引 | 暴力扫描，10 万内毫秒级（`docs/08`） | 单机用户规模远达不到瓶颈 |
| 图数据库 | 超边存在 SQLite 里 | 多跳能力弱于 Zep，但不是当前卖点 |
| 多模态 / 多语言 | 只有文本入口 | 与「人格连续性」主线无关 |
| 托管 SLA / 多地域 | 无 | 托管形态本身放到 M3 |
| 前端产品化 | 单文件 HTML，够用 | 界面不承担验证以外的职责 |
| 云端 embedding 矩阵 | 只有 Ollama / hash | 客户端可自备；托管再补 |

### 2.3 现有前端里会挡住产品化的三处

- **身份在 localStorage**（`docs/13` 第三轮）：角色卡与会话选择存在浏览器，换设备即丢。前端把「租户」当成了本地状态，这正是 §2.1-G1 的界面投影。
- **密钥从界面 POST 进服务端 `.env`**（`docs/13` 第四轮）：单机玩具可以，多用户/托管下不成立（§2.1-G7）。
- **建卡向导不挂记忆管线**（`docs/13` 第十轮「纯前端状态机」）：它证明 UI 与内核之间没有契约，只有约定。产品化的 UI 必须只调用接入契约，不许绕过。

界面其余问题（视觉、移动端、计量展示）不列入产品缺口。

## 3. 接入契约：harness 怎么被用起来

### 3.1 把「三件套」拆成三层，分别可接

| 层 | 现在 | 拆后 | 谁负责 |
|---|---|---|---|
| 生命周期 | `Harness.wake/turn/sleep` 三方法（`harness.py`） | ① 宿主自管循环 → **四个钩子事件**：`session_start / pre_prompt / post_turn / session_end`；② 我们管循环 → 保留 `Harness` | 接入方选一种 |
| 注入 | `turn` 内部拼 system 字符串（`harness.py:129`） | 纯函数 `context(query, space, budget) -> 结构化对象`，再给一个文本渲染器 | 双方都用同一份 |
| 工具 | `alaya/tools.py` 五工具（OpenAI schema）+ `dispatch` | 协议无关 schema + dispatcher；OpenAI 与 MCP 各写一层 30 行映射 | 接入方决定暴露哪几个 |
| 节拍 | `tick` 方法 + `_spawn` 后台线程 | 移进守护进程调度器；宿主侧只保留「可选的立即触发」 | 服务端，不交给宿主 |

关键判断：**注入必须是纯函数，不能长在 turn 里**。否则宿主自己管循环时，只能整段复制 harness 的逻辑——这正是「每个接入方做成一坨不同的东西」的来源（`docs/12` §2 已警告过）。

四个钩子的载荷建议（宿主侧只需实现调用，不需要懂记忆内部）：

```
session_start(space, conversation)          -> {persona_text, resident_text, inbox, degraded}
pre_prompt   (space, conversation, query, budget)
                                            -> {system_prefix, memory_text, tokens, abstained}
post_turn    (space, conversation, user_text, assistant_text, tool_calls)
                                            -> {queued: true}                 # 立即返回
session_end  (space, conversation)          -> {job_id}                      # 异步；结算/整理/做梦
```

三条纪律：所有钩子**幂等**（同一 conversation + 文本 + 时间窗重复调用不产生第二条记忆）；`pre_prompt` **绝不超预算**、拿不到就返回空而不是硬凑；`session_end` **立即返回 job_id**，绝不把十几秒的整理挂在宿主的退出流程上。

### 3.2 四类接入方的适配差异与最小改动

| 接入方 | 谁拥有循环 | 现在能否直接用 | 缺的适配 | 最小改动 | 拿不到的价值 |
|---|---|---|---|---|---|
| **自建 Python agent** | 接入方（调我们的库） | 能，四行接入 | 无对话历史入参、无流式、无异步、无事件钩子；`turn` 只发 system+当前句（`harness.py:129-138`） | `turn(history=None, extra_system=None)`；`async turn_async`；`on_event(kind, payload)`；`build_only(query)` | 若接入方自组 messages，需传 `exclude_ids` 防重复注入（接口已有） |
| **Claude Code 类宿主**（自己管 loop 与工具） | 宿主 | 不能当 Harness 用；可当 sidecar | 只有 HTTP 端点，没有钩子语义；`/v1/context` 已存在但没人用 | 官方 `hooks` 适配器：`SessionStart→wake+context`、`UserPromptSubmit→注入 context_text`、`Stop/PostToolUse→observe`、`SessionEnd→sleep`；全部走 REST，不改内核 | 我们无法保证「每轮都注入」；模型是否用记忆由宿主决定 |
| **MCP 客户端** | 客户端 | 不能 | 无 MCP server；无 resources；无远程鉴权 | `alaya/mcp_server.py`：5 个写工具 + 2 个只读（`memory_status`/`memory_timeline`）、resources（persona/state/resident）、stdio + streamable HTTP、Bearer + space 头 | 没有 wake/sleep 语义，自动注入不存在；工具 schema 已兼容，映射成本低但**价值估计只到五到六成** |
| **OpenAI function calling / Responses** | 接入方 | 只到 schema 兼容，链路没通 | `LLM.chat` 不接收 `tools`（`alaya/core/llm.py:57`）；服务侧 `llm_call` 恒返回 `tool_calls=[]`（`app.py:139-157`），五工具是死代码；tool 消息缺 `tool_call_id`；usage 被丢弃 | 扩 `LLM.chat(tools, tool_choice)` 并解析 `tool_calls`（arguments 是 JSON 串）；`_run_loop` 补 `tool_call_id`；usage 落库 | 无。这类接入方本来就是 harness 的理想用户，接通即完整价值 |

两个必须提前定的细节：

- **工具轮上限**保持 3（`harness.py:27`），但超限收尾要可配置；工具结果必须保留失败原因（现约定很好，别改）。
- **同步回调的签名**（`llm_callable(messages, tools) -> dict`）要升级成能返回 `usage` 与 `finish_reason`，否则成本与截断观测无从下手。

### 3.3 生产里的线程 / 进程模型

```
单进程（默认）：
  HTTP/库调用线程 ──> Memory（thread-local sqlite 连接）
  enrich 线程池(2) ──> 写事实/状态（BEGIN IMMEDIATE，busy 时重试 2 次）
  tick 线程(≤2) ────> review / dream（调 deep LLM，秒级）
  调度线程(缺) ─────> 每 60s 扫 due jobs / due spaces

多进程（现在没有）：
  uvicorn --workers N 会得到 N 份 Memory、N 个线程池、N 套节拍
  SQLite 单写者：N 份写互相抢锁；缓存/降级状态各自为政
```

必须补的三件：**持久 jobs 表 + 单写者队列**（把 enrich、dream、review、forget 都变成可重放任务）；**调度器选主**（DB 租约表，多进程只有主 worker 跑节拍）；**关停协议**（`Harness.join` 已有，服务层要在 lifespan 里调用并把未完成任务落库而不是丢弃）。

### 3.4 多会话并发的锁与隔离

| 问题 | 现状 | 应有 |
|---|---|---|
| 读请求也写库 | 每次 `recall` 写 `retrieval_log` + 对命中项写 `_touch`（两笔写事务） | 日志与计数异步批量写；读路径零写 |
| 同会话并发 turn | 无 per-session 锁，两次 turn 可交错 ingest / 工具写 | 会话级串行（单写者队列 keyed by conversation） |
| 跨会话写 | SQLite 单写者，busy 3s 后失败 | 单写者模型，或在托管形态换 Postgres 行锁 |
| 隔离 | `session_id` 客户端自报，`_no_wildcard` 只拦 `*` | space 从凭证推导；所有查询强制带 space |
| 后台节拍重复 | 多 worker 会各自跑 | 租约选主；任务幂等键 |

量化基线：`docs/08` 记录过并发写 3.75% 失败（已退避重试但未做 30 分钟压测），这是**产品化的入场测试**，不是可选优化。

## 4. 部署 · 成本 · 可观测 · 评测 · 降级

### 4.1 部署形态四档

| 档 | 交付物 | 依赖 | 现状 |
|---|---|---|---|
| 进程内库 | `pip install alaya-memory` | Python + SQLite(FTS5) | 无打包件，`alaya/__init__.py` 只导出 `Memory/Config` |
| 本地服务 | `alaya serve` + `alaya daemon`（调度 + MCP stdio） | 单文件 DB；可选 Ollama | serve 有，daemon 无，无 TLS/鉴权/健康检查规范（仅 `/health`） |
| 容器自托管 | 镜像 + 卷 + 环境注入密钥 | 同上 | 无 Dockerfile |
| 托管 | 多租户 API + 控制台 + 计费 | Postgres/pgvector + 队列 + KMS | 无，且 `docs/01` 明确列为非目标 |

### 4.2 成本（量级估算，待实测）

| 路径 | 每次调用 token 量级 | 估算依据 |
|---|---|---|
| 一轮对话注入 | 输入 1.5k–5k，输出 ≤400 | 人格 ≤7600 字 + 常驻 ≤1500 字 + 检索 ≤1400 token + 系统提示；服务侧 `max_tokens=400`（`app.py:156`） |
| 一条消息抽取 | 输入 1k–2.5k，输出 ≤700 | `extract.py` 一次 `chat_json`，`max_tokens=700` |
| 一次「打烊」 | 合计 15k–40k | 4 页重建各 1 次（`pages.py:109-152`）+ 归纳 1 次 + 做梦 1-2 次（`dream.py:217,237`）+ 折叠按超边数（`forget.py:173`）；**同步跑在请求里** |

结论（按主流国产云端混合价约 ¥2/M 估）：记忆层自身开销约 **¥0.5–2 / 天 / 活跃用户**；主聊天模型另计。**钱不是瓶颈**。真正的成本是：

- **时间**：本地 2B 抽取实测 2–10 秒/条；打烊同步 4 页 + 做梦，云端也要数秒到数十秒，用户会以为卡死（`docs/13` 第一轮就是这个现象）。
- **尾部不可控**：做梦材料最多重放 30 条（`dream.py:35`），折叠按超边数，单次打烊的调用次数随数据增长，没有上限也没有预算。
- **无熔断的降级**：Ollama 半死（TCP 通但不回）时，`embedder.embed` 每次都先打远程再等 `timeout=8s`（`embed.py:54-72`），新文本必然 LRU miss——写入和检索都会被拖到超时。`degraded=True` 之后也**不短路**。
- **缺失的计量**：`TurnResult.latency_ms/token` 只回给调用方，不落库；没有按 space 的成本台账。

### 4.3 可观测性

| 已有 | 缺 | 补法 |
|---|---|---|
| `retrieval_log`（查询、plan、选中、排除、耗时、拒答） | 无 turn 级指标落库；无 trace id；无聚合查询；无告警 | `turn_log` 表（space、latency、注入 token、工具轮、模型 usage、降级标记）+ `/metrics`（Prometheus 文本）+ 结构化日志 `event=` 键 |
| `/v1/stats`：calls/failures/degraded | 失败原因没分类（密钥/超时/限流）；`llm.last_error` 只留最后一次 | 错误码分类计数；key 探活（`docs/13` 第七轮已列为待办） |
| 统一响应带 `retryable` | 队列积压、任务重试次数不可见 | jobs 表暴露 `/v1/jobs`；积压阈值告警 |

### 4.4 评测（15 项机制测试之外）

现有测试是**机制回归**（幂等、状态转移、极性、时间旅行、预算、拒答、冷却、墓碑、人格预算），用 FakeLLM 与真实模型解耦，这是对的，别动。缺的是**质量回归**：

| 指标 | 怎么建 | 门槛 |
|---|---|---|
| 抽取质量 | 200 段真实对话 + 人工标注（实体/事实/状态槽）；算 P/R/F1，状态槽单独看 | 记对率 ≥90%，记全率 ≥80%（`docs/13` 第六轮现状 80%/60%） |
| 召回质量 | LongMemEval 风格题集：时序、多跳、知识更新、偏好四类 | 每类单独报；对标第三方公开数字时注明口径 |
| 拒答 | 标注「该拒答/该召回」集合；算 precision/recall | 误召 ≤10%，拒答阈值由标注集决定，不再猜 |
| 时间旅行 | 「某时刻快照」金标题 | 100% |
| 人格稳定 | 长程脚本：200 轮后 identity 条目未漂移、单会话 promote ≤2 | 0 漂移 |
| 成本/延迟 | 每轮注入 token、打烊调用数、p50/p95 | 打烊 P95 < 5s（异步化后） |

跑法：nightly 对真实 provider 跑（不进 PR 门），发版前跑全量并出报告；权重/阈值改动按 G2 走 A/B。

### 4.5 失败降级矩阵

| 缺失 | 现在的行为 | 漏洞 | 应有 |
|---|---|---|---|
| Ollama embedding 不在 | 降级 hash，写 NULL 向量，FTS+图兜底，`stats.degraded=true` | 无熔断，每次仍等远程超时；恢复后 NULL 行**永不重算**（无 backfill） | 断路器 + 降级期只打一次探活；恢复后后台重算 NULL embedding |
| 云端 LLM 401/超时 | 抽取回退规则；主对话抛 `llm_unavailable` 503 | 401 与超时对用户不可区分（`last_error` 有但不暴露）；规则抽取覆盖率很低 | 错误码分类 + 设置页探活 + 明确文案 |
| dreaming 失败 | harness `sleep` 里 try/except，返回 `dream_error` | 静默跳过，没人知道节拍没跑 | 任务失败进 jobs 重试，连续失败告警 |
| 数据库锁 | 2 次退避后抛错 | 高并发下 5xx | 单写者队列 + 请求排队上限 + 429 |
| 全离线 | `rule` 抽取 + `hash` 向量可跑 | 质量不可用，仅可演示 | 官方明示「离线模式=演示级」，不承诺质量 |

原则不变：**降级必须显式可见**（`docs/03` §6 已立），产品化要把「可见」从 stats 提升到界面与告警。

### 4.6 安全与密钥

| 项 | 现状 | 产品化要求 |
|---|---|---|
| 身份 | 无 | API key / token；space 由凭证推导 |
| 密钥存储 | `.env` 明文；Windows chmod 无效 | 环境注入 / 系统密钥库；服务端不落盘 |
| 运行时改密钥 | `POST /v1/settings` 写 `.env` 并可改 `openai_base` | 单机可保留；托管必须禁用或改为受审计的管理员操作 |
| 数据删除 | 墓碑（不可复活）+ `/v1/wipe` 无鉴权 | 墓碑保留为默认；补**合规硬删**通道（用户要求彻底删除） |
| 传输 | 无 TLS | 本地回环可免；远程必须 TLS 或置于反代后 |

### 5.2 我们的差异化：站得住与站不住

| 主张 | 竞品现状 | 判断 |
|---|---|---|
| **当前状态是派生快照，不是检索结果**：`state_slot` 有「同一 (scope,slot) 至多一条 open」不变式，且每轮必注入 | Letta 的 memory block 每轮注入，但是自由文本、无不变式、无 as-of；Zep 是边级 validity window；Mem0 无原生时序。差异不在「只有我们不检索」，而在「派生快照 + 不变式 + 任意时刻回看」 | **可当卖点**，且最难抄（要五层投影才成立） |
| **人格预算与升格闸门**：7600 字独立预算、整条取舍、工具行为永不进人设、四道闸 + 留痕回滚 | Letta 能自改 memory blocks，但预算隔离与四道闸未见（待验证）；其余无 | **可当卖点**，但要拿「200 轮不漂移」的评测数字支撑 |
| **硬预算注入 + 三级降级**：绝不超预算、性能地板、L0-L3 渐显 | 竞品多为 top-k + rerank，没有「同预算下质量最优」的工程证明 | **可当卖点**，测试已能证明绝不超（`test_never_exceed`） |
| **零外部服务、单文件离线可跑** | Zep 自托管要图库；cognee/Hindsight 要 Postgres；Mem0 自托管要向量库+LLM | **可当卖点**，面向本地优先用户 |
| 「会遗忘 / 会做梦」 | Letta 已有 dreaming（后台 subagent 整合记忆）；Mem0 有记忆过期 | **不能单独当卖点**，只能讲差异（脱敏与情绪衰减，不是整理） |
| 「支持 MCP / 支持函数调用」 | Zep、Letta、Mem0、cognee、Supermemory 全有 | **入场券**，不是差异 |
| 公开 benchmark 分数 | 竞品有；我们一个都没跑过 | **当前是短板**，M2 必须补，补之前不许引用对标数字 |

### 5.3 最值得警惕的是谁

- **Letta（第一顺位）**：它占的正是我们要讲的位置——有状态身份、自改记忆、dreaming、MCP、开源、桌面/CLI、$20/月。它的问题在「agent 平台」而非「陪伴记忆」，但叙事重叠度最高，用户会拿它当替代品。
- **Hindsight（第二顺位）**：架构叙事与我们几乎同构（多路检索 + 重排 + 嵌入式存储 + MCP-first），并且已经带着公开评测数字。它证明「这套架构不是我们独有」。
- **Zep（第三顺位）**：时序图谱 + 企业合规，会把「时间旅行」当成它的固有卖点；我们必须在「派生状态快照」上讲清区别，否则被归为同类。

Mem0 是流量入口与默认选项，但它的强项是生态与托管，不是记忆模型——不构成叙事威胁。

## 6. 三种产品形态 + 推荐主线 + 里程碑

### 6.1 对比

| 维度 | ① 可嵌入 Python 库 | ② 本地记忆服务 + MCP | ③ 托管记忆 API |
|---|---|---|---|
| 目标用户 | 自建 agent 的开发者、陪伴类产品团队（有后端能力） | 重度 AI 工具用户、本地优先团队、独立开发者 | 需要 SLA/合规的产品团队 |
| 交付物 | pip 包 + `Memory`/`Harness` + 接入文档 + 适配器 | `alaya daemon`（REST + MCP + 调度）+ 安装包/容器 + 桌面壳（可选） | REST + SDK + 控制台 + 计费 + 状态页 |
| 工程补齐 | 打包/版本、公共 API 稳定、线程与异步契约、provider 矩阵、迁移 | 持久 jobs、调度选主、MCP、鉴权、打包（PyInstaller/pywebview）、本地备份 | 多租户、Postgres、KMS、配额计费、数据删除权、SRE |
| 变现与开源边界 | 开源内核 + 商业支持/企业插件 | 开源核心 + Pro（加密备份/多设备同步/团队共享空间/托管抽取额度） | 纯商业，可 BYOC |
| 风险 | 与 Mem0 OSS 正面竞争，付费意愿低 | MCP 是窗口期入场券，竞品都有；本地安装体验难做 | 资本与信任门槛高，接口商品化 |
| 判断 | 作为同一内核的发布面保留 | **主线** | 有明确付费客户再做 |

### 6.2 推荐主线与理由

**主线 = ② 本地记忆服务 + MCP，内核同时以 ① 库的形式发布；③ 延后。**

1. 差异化只在「接入方能提供生命周期钩子」的形态里成立。MCP-only 会被降级成检索工具（§3.2），等于把最强的三层能力（常驻注入、人格预算、会话结算）拱手让掉。
2. 目标用户与现有资产匹配：目标用户已经有自己的模型与前端（现有界面只是壳），缺的是记忆运行时；我们卖的是**契约 + 引擎**，不是聊天应用。
3. 分发成本最低：本地一条命令启动、数据在用户手里，绕开托管所需的信任与合规；同时用 MCP/插件进入 Claude Code、Codex 这类宿主做获客。

### 6.3 分期里程碑（每期可独立验收）

| 期 | 周期 | 交付 | 验收（可独立判定） |
|---|---|---|---|
| **M0 契约与可靠性** | 3–4 周 | `pyproject` 可装；`space_id` 贯穿；Bearer 鉴权；`jobs` 表 + 补偿扫描；打烊异步化；会话锁；turn/recall 指标落库；embedding 熔断与回算 | kill -9 后 100% 未抽取 episode 在 5 分钟内补齐；8 会话并发 30 分钟 0 失败；打烊 P95 < 5s |
| **M1 守护进程 + 四类接入** | 4–6 周 | `alaya daemon`（worker + 调度 + 租约）；MCP server（stdio/HTTP）；hooks 适配器；OpenAI tools 真正接通（含 `tool_call_id` 与 usage）；安装包 | Claude Code 类宿主 5 分钟接入并连用 3 天不忘事；无人操作下节拍按点发生；`pip install` 到首条记忆 < 10 分钟 |
| **M2 评测与质量门** | 4 周 | golden set（200 段）+ 六指标 + nightly 回归；拒答阈值标定报告；A/B 框架；成本台账 | 发版指标不退化；拒答阈值来自标注集；单 space 成本上限可配并可观测 |
| **M3 托管 / BYOC（可选）** | 6–8 周 | Postgres 存储适配；多租户与 KMS；配额计费；备份恢复；删除权；SLO | 单租户故障隔离可测；删除请求 24h 内可证明完成；有第一个付费客户才启动 |

## 7. 边界清单：必须放弃 / 必须坚持

### 7.1 必须放弃（产品化后不再成立）

| 原边界 | 出处 | 为什么必须放弃 | 改成什么 |
|---|---|---|---|
| 「不做前端」= 不提供任何可视化 | `docs/12` §7 | 记忆对不对必须能被人看见，否则无法验收也无法排障 | 保留检查台（`/debug`）与只读记忆抽屉，作为**验收工具**而非产品 |
| 「不做多租户 SaaS、不做权限体系」 | `docs/01` 非目标 | 只要离开 loopback 就必须有身份；但可分两级：M0 做 space/鉴权，M3 才做 SaaS | M0 单用户多空间；M3 多租户 |
| 「单机单进程」作为承诺 | README 已知限制 | 多客户端、多 worker 是真实场景 | 默认单机，架构预留单写者与租约 |
| 「会话必须显式关闭」 | README 已知限制 | 用户不会点「打烊」 | 服务端 idle 自动 sleep |
| 「永不物理删除」 | `docs/02` | 合规与用户删除权是硬要求 | 默认墓碑；补硬删通道 |
| 「抽取默认本地 2B」 | `config.py:162` | 实测 2B 撑不住抽取与扮演（`docs/13` 第五轮） | 默认云端小模型；本地仅离线降级 |
| 「常驻活文档手动重建」 | README 已知限制 | 每轮注入的东西不能靠人维护 | 调度器自动重建 |
| 「零第三方依赖」绝对化 | `docs/01` R4 | 打包、HTTP、numpy 都是依赖 | 内核保持标准库优先；服务/托管层允许依赖，用 extras 隔离 |
| 「session_id 即租户」 | 代码现状 | 这是 G1 的根因 | space + conversation 两层 |

### 7.2 必须坚持（改了就不是这个产品）

1. **五层投影、可回溯**：摘要永远不能替代原文；任何上层结论都能回到 episode。
2. **双时间 + 状态快照不变式**：`(scope, slot)` 同时刻至多一条 open；旧值失效但留痕。
3. **三档注入预算互相独立**：人格、常驻、检索不可挪用；人格永不被挤掉。
4. **绝不超预算 + 性能地板**：宁可少注入，不截半句。
5. **升格闸门**：工具行为、单次情绪永不进人设；改人设有频率/幅度/来源/留痕四道闸。
6. **主动记忆四段结构**：只有 `what` 的不进笔记层。
7. **降级显式可见**，不静默降级。
8. **工具少而够用（5 个）**，失败必须返回原因。
9. **不做人格自动演进**：不自动写日记、不自动改人设——这是产品伦理边界，不是技术限制。
10. **契约纪律**：打分公式、预算算法改动走版本化与 A/B，不在产品里随手调。
11. **对外只说功能、不用唯识隐喻**（`docs/06` 三条边界）。
