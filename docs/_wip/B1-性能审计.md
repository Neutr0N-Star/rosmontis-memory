## 0. 结论（先看这三条）

**最慢的三条路径**（100k 档，p50；1k/20k 列同一路径同口径）：

| # | 路径 | 100k | 20k | 1k | 主导项 |
|---|---|---|---|---|---|
| 1 | `Memory.forget`（完整遗忘周期） | **16154 ms**（32,161 条 SQL） | 2835 ms | 5.1 ms | 每条冷条目的 N+1 查询 + 逐条状态机 |
| 2 | `Memory.recall`（端到端，含写库） | **3243 ms**（p95 3382） | 834 ms | 46 ms | `_dense` 占 85–87% |
| 3 | `Memory.close_session`（不含 auto_forget） | **356 ms** | 24.8 ms | 3.5 ms | 300 条逐条 UPDATE + pages/notebook 查询 |

补充两笔按路径计的隐性成本：① 默认 `auto_forget=True` 时 `close_session` 末尾会再跑一次 `forget`，20k 实测 **2653.6 ms**（100k 未直接测，按 forget 实测推为 16 s 量级）；② 任何写入/更新事实的 `ingest` 会额外触发内联衰减，100k **+839 ms**、20k **+393~537 ms**，这是对话热路径上真正的秒级尾部（`ingest` 本身 p50 仅 97 ms）。

**最大的一条优化收益（不改架构）**：dense 取数链路加索引 + 重写 SQL + 缩小取数窗口，100k 从 **2674–2820 ms → 约 100 ms**（-96%），20k 从 698 ms → 约 100–120 ms。窗口 5000 下 episode 取数 43 ms、fact 按同表线性折算约 40 ms 是实测/折算分项之和（fact 窗口未单独建样，报告中已标「估」），其余分项（join/norms/matmul/过滤）均实测。

**需要改架构才能拿的一条**：把热窗口向量做成**进程内常驻连续矩阵**，用内存换掉每次查询的「取 2 万行 BLOB + 拼 buffer + 归一化」。实测同一查询纯点积 1.5–2.2 ms，20k 条向量矩阵仅 82 MB。代价是缓存生命周期与写失效（enrich/dream/forget 都会改向量），估 3–5 人日。

## 1. 测量口径（读数字前必读）

- **分级库**：`bench/_profile/prof_common.py:build_db()` 直接写 schema v3。行数口径：episode=N，fact=0.4N，entity=0.15N，hyperedge=N/20；episode/fact 全部带 **1024 维 float32 向量（4 KB/条）**，向量的方向按话题共线构造（同话题余弦≈0.9），模拟真实 embedding 的相关性分布；FTS 按 `text.tokenize` 同款二元组写。固定时钟 `NOW=1792368000`。
- **为什么不用真库**：真库只有 182 episode / 1.72 MB（v2 schema），只能做冒烟；实测其副本 recall 1.3–4.7 ms，没有规模信息。100k 档库文件 702 MB、20k 档 140 MB。
- **embedding 用 hash 但 `degraded=False`**（`ProfileEmbedder`）：生产 hash 兜底时 `write.py:98-99` 不落伪向量，dense 路会整条消失，无法测扫描；本审计让写路径真的落 4 KB 向量，**扫描成本与接 bge-m3 时一致**，但相关性分值不可用于质量结论。
- **延迟是单机测量**：绝对值受机器负载影响；p95 在 1k/20k 档 n=10/6 次、100k 档部分指标 n=3，100k 的 p95 近似取 max。
- **既有基准不可直接比**：`bench/report.md` 的 p95=6 ms 是 400 集库 + 向量未落库（dense 退化）的口径；本审计 1k 档 46 ms 的差异几乎全部来自「真的有 4 KB 向量要扫」。任务线索「1.98 万条 dense p50≈388 ms」与本审计的向量条数单价落在同一区间：1k 档 22 ms / 1400 条 ≈ 15.7 µs/条，20k 档 690 ms / 28,000 条 ≈ 24.6 µs/条，由此折算 19.8k 条约 0.31–0.49 s，388 ms 落在区间内。注意本审计 20k 档是 **2.8 万条向量**（2 万 episode + 8 千 fact），所以实测 0.68–0.72 s。

### 2.2 dense 拆解（单次 p50，ms）

| 档 | dense 合计 | episode 取数 | fact 取数 | 其中排序/全扫 | b"".join | norms | matmul | Python 过滤+排序 |
|---|---|---|---|---|---|---|---|---|
| 20k | 698 | 449 | 112 | **189** | 30 | 58 | 3.1 | 2.3 |
| 100k | 2778 | 2059 | 550 | **2144** | 48 | 85 | 3.9 | 5.5 |

- `EXPLAIN QUERY PLAN` 实测：`SCAN episode` / `SCAN fact` + `USE TEMP B-TREE FOR ORDER BY`（两处 SQL 在 `recall.py:605-611`、`recall.py:617-623`，`LIMIT 20000` 硬编码在 `:609`、`:621`）。20k 档扫 2 万行（80 MB）再排序，100k 档**扫 10 万行（400 MB）再排序后只取 2 万行**；成本随全表行数线性增长，`LIMIT 20000` 没有把成本封顶——5 倍数据对应 4~5 倍 dense 延迟。
- 拆法：在库副本上建 `(session_id, t_ingest DESC)` 索引后，同一 SQL 的取数降到 301 ms（episode）/164 ms（fact），可反推排序/全扫部分 = 2059-301 + 550-164 ≈ **2144 ms（占 dense 77%）**。纯点在内存里只花 150 ms。
- **取数窗口是第二个乘数**（带索引实测，episode 表）：LIMIT 20000 → 302 ms；10000 → 152 ms；5000 → 43 ms；2000 → 17 ms。线性。
- 建索引后跑**未修改的** `_dense`：100k **1067 ms**（-62%），20k 664 ms（-5%，20k 排序规模小，索引收益低）。
- 内存：单次 dense 峰值工作集 20k 档 527–752 MB、100k 档 628–912 MB（采样窗口不同，量级可信）；`PRAGMA cache_size` 从 32 MB 调到 256 MB **无收益**（100k 2612 → 2661 ms），不要做。

- `enrich` 0.9 ms（100k）/0.31 ms（20k），9 条 SQL，非瓶颈。
- `dream` 104.7 ms（100k，重放 30 条 + `_bind` + 一次 submit + dream_log），非瓶颈。

## 3. 优化清单 A：不改架构就能拿到

> 每项格式：**现状 → 预期 → 成本 → 风险 → 怎么测**。预期数字来自实测拆解；标「估」的是按测得的单价推算。

### O1 去掉 `(?='*' OR col=?)` 绑定参数反模式（多处）

- **file:line**：`recall.py:561-568`（常驻）、`recall.py:605-611`/`617-623`（dense）、`recall.py:682-689`（sparse）、`recall.py:717-722`（graph 实体）、`field.py:194-200`/`238-245`/`267-275`（三路点火）、`forget.py:68-75`/`105-113`（衰减/遗忘扫描）。
- **现状**：绑定参数让 `session_id` 上的索引在 prepare 阶段不可用 → 全表扫。`_collect_states` 100k 每次 **95.2 ms 返回 0 行**；20k 3.3–3.8 ms；1k 0.2 ms。
- **预期**：同一 SQL 改成显式分支后 100k **0.01 ms**（实测）；每次 recall 固定省 ≈95 ms（-2.9%），20k 省 ≈3.5 ms。同时这是 O2/O3 生效的前提。
- **成本**：0.5 人日。
- **风险**：低。跨会话查询（`'*'`）语义必须保留成分支 SQL；改动面 10+ 处，漏改一处就少省一段。`_log` 的 `retrieval_log` 不受影响。
- **怎么测**：`bench/_profile/bench_read.py` 看 `routes.states` 与 `recall_e2e`；质量看 `bench/pareto.py` 的 nDCG@10 与四类 acc 全不劣。

### O2 给 episode / fact 建 `(session_id, t_ingest DESC)` 索引

- **file:line**：`schema.sql:81-87`（episode 索引块）、`schema.sql:140-143`（fact）；查询在 `recall.py:605-611`、`617-623`。
- **现状**：dense 100k 2673.9–2820.5 ms、20k 671.6–698.7 ms；EXPLAIN 为 `SCAN` + `USE TEMP B-TREE FOR ORDER BY`。
- **预期**：**不改 SQL**、只建索引，同一 `_dense` 实测 **100k 1067 ms（-62%）**、20k 664 ms（-5%）。
- **成本**：0.2 人日（schema + 幂等迁移）。一次性建索引在 100k 库实测 0.95 s（本次实验共建了 4 个索引）。
- **风险**：低。写路径每行多维护一个索引（写入略增，需复测 O7 的 ingest）；索引不含 BLOB 列，库体积增量 <1%。
- **怎么测**：`bench/_profile/bench_micro.py` 的 `current.plan_*`（必须由 SCAN 变 SEARCH）+ `indexed.dense_now_with_index`；`bench/pareto.py` 确认质量不变。

### O3 dense 取数窗口 `LIMIT 20000` 改为可配置（默认 5000），并重写 SQL 走索引

- **file:line**：`recall.py:609`、`recall.py:621`（硬编码 20000）；`recall.py:598`（`k = plan["_k_dense"]` 已是现成的配置入口）。
- **现状**：100k 即使带索引，取 2 万行/表仍要 episode 302 ms + fact 164 ms = 466 ms；内存里再花 ~150 ms。
- **预期**：索引 + 重写 SQL + 窗口 5000：episode 43 ms（实测）、fact 估 ~40 ms、内存 ~20 ms → **dense 约 100 ms（-96%）**；窗口 2000 时 episode 17 ms（实测）→ 约 60 ms。20k 档：episode 取数 42 ms（实测）+ fact ~30 + 内存 ~35 ≈ **100–120 ms**（现 698 ms）。
- **成本**：0.5 人日 + 质量回归 0.5 人日。
- **风险**：**这是最值得做但质量风险最高的一项**：窗口之外的老记忆不再进 dense 点火（FTS/graph/field 仍可达，冷启动无结构边时影响更大）。时序类题最可能退化。
- **怎么测**：`bench/pareto.py` 扫 2000/5000/10000/20000 四档，画「质量－延迟」前沿；硬判据用 docs/15 D2（top-10 一致率 ≥95% 或改优）＋四类 acc 不劣。

### O4 向量写入时 L2 归一化，查询只做点积

- **file:line**：`vec.py:72-83`（`cosine_batch` 第 80-81 行每次重算 norms，第 82 行除）；写路径 `vec.py:21-26`、`write.py:99`、`pipeline.py:277-279`、`dream.py:134/149`。
- **现状**：100k 每次 dense 的 norms 85 ms（episode 42.1 + fact 42.7，实测），20k 58 ms（占 8%）；纯点积同一矩阵 **2.2 ms**（实测）。
- **预期**：省 58–85 ms；窗口缩到 5000 后按比例省 ~11 ms。占比不大，但零语义风险。
- **成本**：0.3 人日（含存量向量迁移脚本）。
- **风险**：低。必须确认**所有**写入路径都归一化（直写 `pipeline.submit` 的入口也要），漏一条就静默错分；零向量需保底。
- **怎么测**：改造前后 `cosine` 等价性单测（误差 <1e-6）+ `bench_micro.py` 的 `variant_dot_only`。

### O5 `_refine_cosine` 复用 dense 已取向量，批量算余弦

- **file:line**：`recall.py:865-878`（第 866 行重复 embed、871-874 两条 IN 查询、877 逐条 `V.cosine` → 每条一次 `unpack`）。
- **现状**：100k 5.6 ms、20k 6.1 ms、1k 5.0 ms（实测）。
- **预期**：2–3 ms（向量已在 O3 的窗口里，不必二次取库）。
- **成本**：0.2 人日。
- **风险**：低；只需把 dense 的矩阵/向量缓存传到 refine。
- **怎么测**：`bench_micro.py` 的 `refine_cosine`；top-10 一致率 ≥95%。

### O6 候选回表批量（N+1 → 2 条 IN）

- **file:line**：`recall.py:504-515`（循环逐条 `_load_candidate`）、`recall.py:762-862`（每条一次 SELECT）。
- **现状**：100k 182 条候选逐条回表 4.7 ms、批量 1.9 ms（实测）；20k 5.6 → 2.4 ms。
- **预期**：每次 recall 省 2–3 ms（100k）/3.2 ms（20k），占比 <0.1%，**零风险**。
- **成本**：0.3 人日。
- **风险**：低；可见性与时间过滤改在内存里做，顺序保持 RRF 原序。
- **怎么测**：`bench_micro.py` 的 `candidate_load`；改造前后召回 id 集合逐条 diff 必须为空。

### O7 `seq` 自增查询 O(N) → 覆盖索引或会话计数器

- **file:line**：`pipeline.py:264-267`；索引缺失见 `schema.sql:81-87`。
- **现状**：100k `MAX(seq)` **103.4 ms**（占 ingest/accept 的 ~100%）；20k 2.46 ms；1k 0.07 ms。
- **预期**：加 `(session_id, seq DESC)` 覆盖索引后同一语句 **0.004 ms**（实测）；ingest 97 → 约 2 ms、accept 97 → 约 2 ms（100k），20k 3.7 → ~0.2 ms。
- **成本**：0.2 人日（索引）；0.5 人日（session 行内计数器，事务内 `UPDATE session SET seq=seq+1`）。
- **风险**：低。索引方案仍随会话行数增长，但 O(log N)；计数器方案需保证单写者（`DB.tx` 已是 `BEGIN IMMEDIATE`，成立），迁移时要回填 `max(seq)`。
- **怎么测**：`bench_write.py` 的 `seq_query`/`ingest_sync`/`ingest_accept` 三列；并发写测试确认 seq 唯一。

### O8 `_touch` 逐条 SELECT+UPDATE → 批量

- **file:line**：`memory.py:176-208`（188-206 行每 id 一条 SELECT + 一条 UPDATE，同一事务）。
- **现状**：100k p50 3.5 / p95 28.6 ms；20k 2.5 / 5.9 ms；1k 0.6 / 19.2 ms（首次含建连噪声）。
- **预期**：一条 `UPDATE episode ... WHERE id IN (...) AND tier!='resident'` + important/normal 两条冷却 UPDATE，约 0.3 ms。
- **成本**：0.2 人日。
- **风险**：低；tier 分流即可，注意 `resident` 跳过与 `last_access` 语义不变。
- **怎么测**：`bench_read.py` 的 `touch` 列；改造前后 `access_count/cooldown_until` 全等。

### O9 `_log` 与 `retrieval_log` 体积（不是延迟问题）

- **file:line**：`recall.py:1026-1046`（1030 行每次一个写事务）；`schema.sql:205-218`（无保留策略）。
- **现状**：0.06–0.09 ms/次（实测），延迟占比 <0.01% → **不需要为延迟优化**。但每次 recall 写 1 行含 `plan_json`，长期是无上限增长。
- **预期**：延迟不变；按天或按 N 条淘汰，控制库体积。
- **成本**：0.2 人日。
- **风险**：低；需保留审计窗口（建议 30 天）并确认 `bench`/debug 依赖的字段仍可查。
- **怎么测**：连续 1 万次 recall 后 `retrieval_log` 行数与 db 体积曲线。

### O10 `close_session` 的 300 条逐条 UPDATE 合批

- **file:line**：`memory.py:775-790`。
- **现状**：100k 355.6 ms、20k 24.8 ms、1k 3.5 ms（auto_forget=False，实测）。
- **预期**：峰终两条 UPDATE（peak/tail 分组）后省 5–10 ms；剩余的大头是 pages/notebook/observations 多次查询，需单独拆（估可到 ~150 ms）。
- **成本**：0.3 人日。
- **风险**：低。
- **怎么测**：`bench_write.py` 的 `close_session_no_forget`；cProfile 复核拆分比例。

### O11 forget 的 N+1 与逐条状态机

- **file:line**：`forget.py:128-138`（每条冷条目一次超边查询，5000 次）、`forget.py:204-219`（逐条 `TR.transition`）、`forget.py:151-153`（`next(r for r in edge_map[eid]...)` 线性查找，最坏 O(n²)）、`forget.py:182-189`（每个折叠成员一条 UPDATE）。
- **现状**：100k **16.15 s / 32,161 条 SQL**；20k 2.84 s / 34,060 条。
- **预期**：批量超边查询 4.2 ms（实测）+ 批量归档单事务 305.5 ms（实测）+ 674 次折叠 submit（每次一个事务，估 ~1 ms）→ **1.0–1.5 s（-90%）**；把折叠也批量化可 <1 s。
- **成本**：1.0 人日。
- **风险**：中。`item_state_log` 的 from/to 审计行不能丢，批量走同构 SQL 或保留逐条审计行但共用一个事务；失败回滚面变大（整批 vs 单条跳过），需要 per-id 错误收集。
- **怎么测**：`bench_write.py` 的 `forget.p50` 与 `n_sql`；`alaya.core.audit` + `bench/pareto.py` 确认归档条数、state_log 行数、状态一致；再测 100 次连续 forget 不泄漏。

### O12 内联衰减移出写热路径

- **file:line**：`write.py:159-161`（ingest 后触发）、`write.py:561-567`、`forget.py:61-96`（每次扫 2000 行 + 逐条 transition）。
- **现状**：`auto_forget=True`（`config.py:195` 默认）时，凡写入/更新事实的 ingest 额外付：20k 首 537 ms / 稳 393 ms（归档 1852/1327 条）、100k 839 / 853 ms（各 1999 条）。**这是热路径上最隐蔽的秒级尾部。**
- **预期**：写路径 0 ms；改后台节拍后按 5 min 一次执行，单次成本不变但不在用户请求上。
- **成本**：0.5 人日（复用 `pipeline._get_pool` 或 harness 节拍）～1.5 人日（接 docs/15 §3.5 的 job 表）。
- **风险**：中。归档延后 → 冷条目在窗口内仍参与检索（质量略变）；后台失败需重试与告警（job 表已定义 lease/backoff，正好覆盖）。
- **怎么测**：`bench_write.py` 的 `decay_first/decay_steady` 与 `ingest_sync` 对照；加「后台线程异常不阻塞 accept」的测试。

### O13 打包 MMR 的 O(n²) 与重复 bigram 计算

- **file:line**：`recall.py:913-921`（对候选池逐条 `mmr_factor`）、`score.py:295-322`（对每个已选条目做 jaccard）、`text.py:88-100`（每次现算 bigram set，无缓存）。
- **现状**：100k pack 44.4 ms、20k 55.5 ms、1k 22.9–27.0 ms（实测），占 e2e 1.4–6%；候选池 152–193。
- **预期**：候选级缓存 bigram set + 只与同 kind 已选比较 → 10–15 ms（-70%）。
- **成本**：0.3 人日。
- **风险**：低；MMR 分数语义不变，只是缓存。
- **怎么测**：`bench_read.py` 的 `phases.pack`；top-10 一致率 ≥95%。

### O14 graph 的 N+1（低优先级）

- **file:line**：`recall.py:743-757`（最多 12 个实体各一条超边成员查询）。
- **现状**：100k 8.2 ms、20k 1.3 ms、1k 0.2 ms——不是瓶颈。
- **预期**：批量 IN 后 ~2 ms；**建议排在 O13 之后，不做也不影响大局**。
- **成本/风险**：0.2 人日 / 低。
- **怎么测**：`bench_read.py` 的 `routes.*.graph` + 召回 id diff。

### O15 field deep 的扩散成本（当前 ~229 ms）

- **file:line**：`field.py:510-587`（propagate）、`field.py:493-507`（每轮 `_neighbors`）、`field.py:373-429`（结构边最多 3000 成员两两建边）、`field.py:432-490`（`_fact_edges` 的 OR 查询）。
- **现状**：100k deep field 229 ms = seed 3.5 + propagate(3 轮) 123.6 + `_visible_keys(phi)` 10.1 + 其余；propagate 单轮实测 25.6 / 66.9 / 127.5 ms（1/2/3 轮），第 3 轮涨最快是前沿节点数膨胀（phi 3874 个节点）。`_fact_edges` 单次 16.6 ms（实测），拆成 4 条索引化查询 17.0 ms——**拆分无收益，OR 不是这里的主因**。
- **预期**：给每轮前沿设上限（如 500 节点）+ 复用邻接 + 过滤后再扩散，估 229 → 80–120 ms；属质量/成本折中，必须用 pq 前沿判。
- **成本**：0.5 人日。
- **风险**：中；扩散深度直接对应「多跳」能力，docs/15 已把 hops 写进反射深度。
- **怎么测**：`bench/pareto.py` 的多跳 acc；`bench_read.py` 的 `routes.deep.field`。

### 不做（实测无收益）

- **调大 `PRAGMA cache_size`**：32 MB → 256 MB，100k dense 2612 → 2661 ms（无收益）；瓶颈是排序/拷贝不是页缓存。
- **int8 量化扫描**：numpy 无量化 GEMM，实测反量化后 24.4 ms vs float32 点积 2.2 ms，**慢 11 倍**；20k 矩阵 82 MB 也不是内存瓶颈的主因。不要做。

## 4. 优化清单 B：要改架构才能拿到

### A1 进程内常驻向量矩阵（热窗口缓存）

- **现状**：100k dense 2.67–2.82 s；同数据纯点积实测 1.5–2.2 ms，20k 条 episode 向量矩阵 82 MB（实测 `nbytes`），缓存加载 9–11 ms（已含在进程内构造）。
- **方案**：启动/写入后异步把「热窗口」向量装进连续 float32 矩阵（建议 5000–20000 条，20–82 MB；100k 全量 410 MB 不建议）；用 `(session_id, t_ingest)` 的版本号做增量；`_dense` 直接矩阵点积 + `argpartition`。
- **预期**：dense **2.75 s → 2–5 ms**；首次加载 0.5–2 s 可接受；峰值内存 ≤ 现 dense 的 0.6–0.9 GB。
- **成本**：3–5 人日（缓存生命周期、写失效、并发、降级、迁移）。
- **风险**：高。enrich/dream/forget/订正都会改向量或可见性，失效广播漏一条就召回陈旧；内存上限必须可配；无 numpy/降级环境要有回退路径。
- **怎么测**：改造前后 dense top-40 一致率 ≥99%；`bench_read.py` 延迟；`bench/pareto.py` 质量；24 h 长跑内存曲线与写失效注入测试。

### A2 ANN 索引替代精确扫描

- **现状**：精确扫描算力只占 2 ms，剩下全是 I/O、排序与拷贝；做完 O2+O3+A1 后 dense 已到 ~100 ms / ~5 ms 量级，10 万规模下 ANN 的边际收益有限。
- **方案**：自写 IVF/PQ 或用 numpy 实现的 HNSW 需要新依赖或大量维护，且 docs/15 §5 明确「不引入需运维的外部服务」。
- **预期**：召回损失换延迟；在当前规模**不推荐先做**。
- **成本**：5–8 人日；**风险：高**（质量 + 维护）。
- **怎么测**：recall@10 vs 精确扫描，`bench/pareto.py` 全量。

### A3 维护作业后台化（job 表落地）

- **现状**：`api.Handle.settle` 已有 job_id（`api.py:252-314`），但 `forget`/内联衰减/`close_session` 沉淀仍可在请求里同步跑（`memory.py:745-810`、`write.py:159-161`）。
- **方案**：把 O12 的衰减、close_session 的 pages/notebook/observations、forget 全部投到 docs/15 §3.5 定义的 `job` 表，单写者队列 + 租约 + 退避。
- **预期**：写路径 P95 从秒级回到毫秒级；后台 CPU 可调度；可重放（D4a）。
- **成本**：2–3 人日；**风险**：中（幂等键、选主、失败退避）。
- **怎么测**：settle 立即返回的时延；kill 后台再重放的终态一致（D4a/D4b）。

### A4 dense 的「近因窗口」语义（属于产品决策，不是纯工程）

- **现状**：`LIMIT 20000` 实际已经在做近因截断，但没有配置项也没有文档化，100k 时等于「只看最近 2 万条」。
- **方案**：把窗口做成 `Config.recall_dense_window` 并在 `recall_log.plan_json` 里记录实际窗口，让「最近 N 条才参与 dense 点火」成为可审计、可调的产品参数；配套 FTS/graph 兜老记忆。
- **预期**：O3 的延迟收益变成可控的质量/成本旋钮。
- **成本**：0.5 人日；**风险**：低（需同步文档 03/15）。

## 5. 建议执行顺序

1. **O7（seq 索引）**：0.2 人日，写路径 97 → 约 2 ms，风险最低，先落。
2. **O1（去 `?='*' OR`）+ O2（索引）**：0.7 人日，其中 O1 单次 recall 省 95 ms；O2 让 dense 100k 2.78 s → 1.07 s。两项一起做，因为 O2 的效果依赖 O1。
3. **O3（窗口 5000）**：dense 到约 100 ms，但**必须配 0.5 人日的质量回归**；用 `bench/pareto.py` 扫四档窗口定默认值。
4. **O12（内联衰减后台化）+ O11（forget 批量化）**：消除写热路径秒级尾部与 16 s 的维护作业。
5. **A1（矩阵常驻）**：前面做完后 dense 仍 >50 ms 再上；否则 10 万规模用不上。
6. 其余 O4–O6、O8–O10、O13 是 0.2–0.5 人日的零/低风险增量，穿插做。
7. **不做**：cache_size、int8、ANN（见 §3 末尾与 A2）。

## 6. 未测 / 局限

- **并发**：单线程测量；`DB.tx` 的 `BEGIN IMMEDIATE` + 15 ms 退避在并发写下的失败率与 P95 未测（`db.py:296` 注释称并发写入实测有 3.75% 失败率，本次未复现）。
- **真向量**：用 hash 向量 + 话题共线构造，扫描与内存数字可信，**相关性分数不可用于质量结论**；真实 bge-m3 的余弦分布会让 `_refine_cosine`/`recall_k` 的效果不同。
- **LLM 延迟**：无 Ollama，`extract` 走规则；接真模型后 ingest/enrich 会被 LLM 时延主导（本报告只覆盖 alaya 自身耗时）。
- **迁移与冷启动**：100k 库从 v2 迁移的耗时、Windows 冷启动 page cache 未单独测；真库副本 v2→v3 迁移在 182 条上瞬时完成。
- **长跑**：WAL 增长、retrieval_log 体积、内存碎片未做 24 h 观测。
