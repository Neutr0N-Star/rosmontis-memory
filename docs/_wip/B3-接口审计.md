## 0. 结论：最严重的三条 + 必须现在处理的兼容性坑

1. **同一套生命周期有两份实现、两套承诺**：Python `Handle(wake/context/turn/observe/settle)` 与 HTTP `/v1/session/wake|sleep`、`/v1/turn`、`/v1/context` 各自实现。`Handle.context` 是纯函数且硬压预算，`/v1/context` 走 `Memory.build_context`：**实测 72 tokens > 调用方 budget=60**，且写 `retrieval_log`；HTTP 又没有 `settle`、没有 `space/conversation`。宿主从 A3 推荐的 REST hooks 接入时，拿不到 §3.3 的任何一条纪律保证。
2. **§3.3/§3.4 的稳定承诺与 §3.5/§4 的验收判据多处落空**：`docs/15:143` 与 `api.py:22-24` 写“所有方法幂等”，但实现口径是“写入 300 秒窗口去重”（`ids.py:21-28`），且 `settle` 完成后再次调用会按新 uuid 建 job 并**再次改写 episode 的 salience/emotion**（实测同一批 episode `0.51→0.66`、`0.75→0.36`、`0.76→1.0`），`observe` 幂等只靠进程内字典（`api.py:219-233`）；`§3.5` 的 `job` 表与 `Config.idle_timeout_s` 在代码中完全不存在（`settle` 是内存线程 + `job_<uuid>`，非确定性 id）；`D3a` 说 `settle` 产出 `origin='system'`，实测只有 `tool`/`dream`；`D3b` 说 Web `/v1/turn` 可注入 `make_llm_callable(fake_llm)`，但 `service/app.py:133-150` 在 Harness 构造时固定用 `mem.llm_hot`，没有注入缝。
3. **v2 旧库不是“能不能跑”的问题，而是“打开即原地改库、无退路”**：副本实测 v2→v3 成功（182/182 行回填），但 `Memory.__init__` 无条件 `DB.init_db`（`memory.py:41`），没有 `migrate=False/read_only/dry_run/备份` 开关（`api.py:437` 也没有）；迁移失败直接 `raise`（`db.py:121`），没有只读降级。**工作区默认 `alaya.db` 仍是 `user_version=2`（182 episodes）**——任何按 README 的 `python run.py serve` 或 `alaya.open("alaya.db")` 都会先改这个库；这和研究/验收要求的“`alaya.db` 只读”直接冲突。
4. 另有一条**当前红测试**：`tests/test_pipeline_closure.py:125` 失败，因为 `bench/_profile/prof_common.py:374（工作树未跟踪）` 直接 `INSERT INTO episode`，违反 §3.1“唯一写入点”；D1“新增测试全绿”目前不成立（`python tests/test_pipeline_closure.py` → FAILED）。

**兼容性坑的直接回答**：v2 旧库 + 新代码**能跑**（自动迁移 + 回填，见 §4.1）；但“**不迁移**跑”**做不到**，也没有备份/回滚/只读路径；默认库正是 v2，升级即写库。这是必须现在决策的兼容性坑。

## 4. 兼容性实测：v2 旧库 + 新代码

### 4.1 实测路径与结果（全部在临时目录，`alaya.db` 只读）

1. 从 `git show 42c7c48:alaya/schema.sql` 造 v2 库（`PRAGMA user_version=2`，无 `episode.state/origin`、无 `item_state_log`），插入 v2 episode/fact 行。
2. `Memory(Config(db_path=..., embed_provider="hash", llm_hot="rule", llm_deep="rule"))`：
   - `user_version 2 → 3`；`episode.state` 列出现；`item_state_log` 出现；旧 episode 回填 `state`（`compat_state`）。
   - `recall` / `ingest` / `tick` / `close_session` 全部 OK（v2 合成库，行数=1）。
3. `alaya.open(v2_copy, {... fake LLM ...})` → `wake` / `context` / `turn` 全 OK（`pure=True`、reply 正常）。
4. 真实库副本：`copy(alaya.db)` → `Memory` 打开 → `user_version 2 → 3`，**182/182 条 episode 回填 state**；源文件仍 `user_version=2`（只读校验）。
5. 结论：**v2 数据可平滑升级**；迁移单事务、失败 ROLLBACK（`db.py:103-122`）。

### 4.2 兼容性坑（按严重度）

- **无“不迁移/只读/预演”入口**：`Memory.__init__` 必调 `DB.init_db`（`memory.py:41`），`DB.connect` 普通读写连接（`db.py:45-60`）；`api.open` 无 `migrate/read_only` 参数（`api.py:437`）。工作区默认 `alaya.db` 是 v2，首次运行即原地升级；与“真库只读”的验收纪律冲突。**必须现在决策**：补 `open(migrate="auto"|"never"|"dry_run")` 或至少默认先备份。
- **迁移失败无降级**：`_migrate` 失败 `raise`（`db.py:121`），`Memory` 不可用，只读查询也做不了；`alaya.open` 把它包成 `open_failed, retryable=True`（`api.py:484`）——迁移失败重试没意义，错误码会误导。
- **只处理“库版本 < 代码版本”**：`if version < SCHEMA_VERSION`（`db.py:89`）；未来库（v4）配旧代码会静默运行，没有“未知版本拒绝”。反向（旧代码 v2 打开新库 v3）未测、无保护。
- **版本纪律只写在文档**：docs/15:152 要求升主版本，但无 CHANGELOG/常量联动/启动校验；工作树并发新增 `pyproject.toml`（1.0.0）不改变这一点。
- **D1 当前不绿**：`tests/test_pipeline_closure.py` 红（见 §0.4），即“新增测试全绿”不成立。
